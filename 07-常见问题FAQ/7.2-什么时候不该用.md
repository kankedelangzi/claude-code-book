# 7.2 什么时候不该用？

> 知道什么时候不用，比知道什么时候用更重要。

## 🎯 一句话原则

**能用键盘三分钟搞定的，别打开 Claude Code。**

---

## ❌ 不该用的场景（详细说明）

### 1. 改一个变量名 / 简单重构 🔄

**错误示范：**
```bash
❌ 把 config.username 改成 config.accountName
```

**正确做法：**
```bash
✅ 编辑器全局替换（Ctrl+Shift+H / Cmd+Shift+H）
   → 10 秒搞定

或者用 Claude Code：
   → 等它读文件、分析、修改、确认... 30 秒
   → 而且它可能改多了或改少了
```

**时间对比：**
| 操作 | 手动 | Claude Code |
|------|------|--------------|
| 改一个变量名 | 10 秒 | 30 秒 |
| 全局替换一个词 | 15 秒 | 40 秒 |
| 格式化代码 | 1 秒 | 20 秒 |

**结论：这种活儿别麻烦 AI。**

---

### 2. 一行代码的事 📝

**错误示范：**
```javascript
❌ Claude Code，帮我写一行代码：console.log('debug:', data);
```

**正确做法：**
```javascript
✅ 直接敲：console.log('debug:', data);
   → 5 秒钟

❌ 用 Claude Code
   → 打开 Claude Code（5 秒）
   → 输入指令（10 秒）
   → 等待响应（10 秒）
   → 确认代码（5 秒）
   → 总共 30 秒
```

**类似的"一行代码"场景：**
```javascript
// 这些别用 Claude Code
let total = arr.reduce((sum, x) => sum + x, 0);
const isAdult = users.filter(u => u.age >= 18);
const data = await fetch(url).then(r => r.json());
console.log('Result:', result);
```

---

### 3. 你还不知道要做什么 🤷

**错误示范：**
```bash
❌ 帮我把这个项目改得更好一点
❌ 优化一下这段代码
❌ 帮我重构一下
```

**这种模糊的需求给谁都头疼。**

**正确做法：**
```bash
✅ 先自己想清楚：
   1. 要改什么？（明确目标）
   2. 改成什么样？（预期结果）
   3. 有什么约束？（不能改的部分）

✅ 然后给 Claude Code 明确的指令：
   "把 UserList 组件从 Class 改成 Function，
   用 hooks 替换生命周期方法，保持功能不变"
```

**Claude Code 需要明确的输入，否则它会给你明确的废话。**

---

### 4. 涉及敏感信息的操作 🔐

**危险示范：**
```bash
❌ 帮我生成一个数据库迁移脚本，用户表里加个字段
❌ 帮我写一个删除测试数据的脚本
❌ 帮我配置生产环境的 Nginx
```

**如果这些操作会直接跑在生产数据库/服务器上——`停止`。**

**涉及以下内容的操作，先自己确认，再决定是否让 Claude Code 参与：**

| 操作类型 | 风险 | 建议做法 |
|---------|------|----------|
| 数据库 schema 变更 | 可能删表、删字段 | 自己写 SQL，review 后再执行 |
| 删除操作（文件、记录、分支） | 可能误删重要数据 | 先备份，再操作 |
| 生产环境部署脚本 | 可能重启服务、清空缓存 | 在测试环境先验证 |
| 权限配置 | 可能开放过高权限 | 最小化权限原则，review 配置 |
| 密钥和证书管理 | 可能泄露敏感信息 | 用密钥管理工具，不要写进代码 |

**正确做法：**
```bash
✅ 让 Claude Code 生成脚本模板
✅ 你仔细 review 每一行
✅ 在测试环境先跑
✅ 确认没问题再到生产环境执行
```

---

### 5. 需要深度理解的业务逻辑 💼

**错误示范：**
```bash
❌ 帮我把这个支付回调的处理逻辑重写一下
❌ 帮我改一下权限校验的逻辑
❌ 帮我优化订单状态机的代码
```

**这些逻辑涉及：**
- 支付流程（钱的事，不能出错）
- 权限控制（安全的事，不能马虎）
- 合规代码（法律的事，不能乱来）

**Claude Code 可以帮你`写`，但不该让它帮你`设计`这种逻辑。**

**正确做法：**
```bash
✅ 你自己设计好逻辑流程（画流程图、写伪代码）
✅ 让 Claude Code 帮你实现细节
✅ 你 review 每一行，确保逻辑正确
✅ 写完整的单元测试
```

**示例：支付回调处理**
```bash
❌ 错误：让 Claude Code 从头设计支付回调逻辑

✅ 正确：
   1. 你设计流程：
      - 验证签名
      - 检查订单状态（防止重复处理）
      - 更新订单状态
      - 记录日志
   
   2. 让 Claude Code 实现：
      "按照我设计的流程，实现支付回调处理函数，
      每个步骤都要加日志，签名验证用 crypto 模块"
   
   3. 你 review 代码，确保逻辑正确
   4. 写完整的测试用例
```

---

### 6. 代码 Review 应该你自己做 👀

**错误示范：**
```bash
❌ 帮我 review 一下这个 PR
```

**Claude Code 可以帮你找出明显的代码问题，但：**
- 它不知道你们的团队编码规范
- 它不了解你们的业务上下文
- 它不会说"这段代码上次上线出了问题，别动"

**正确做法：**
```bash
✅ 用 Claude Code 做 pre-review（初筛）：
   "帮我检查一下这段代码有没有明显的 bug、
   性能问题、安全风险"

✅ 你自己做最终判断：
   - 代码逻辑是否符合业务需求？
   - 有没有边界情况没考虑到？
   - 性能是否可接受？
   - 有没有更好的实现方式？
```

---

### 7. 别在紧急情况下第一次用 🚨

**错误场景：**
```
（线上报警 500）
快快快！帮我修一下！
```

**生产环境出问题时，不是学新工具的好时机。**

**正确做法：**
```bash
✅ 平时就用 Claude Code，熟悉它的能力和局限
✅ 关键时刻才能信任它
✅ 紧急情况先手动修复，稳住局面
✅ 事后用 Claude Code 分析根因，防止再犯
```

**示例：**
```
场景：线上服务 CPU 100%

❌ 错误：第一次用 Claude Code，手忙脚乱

✅ 正确：
   1. 手动重启服务，先稳住（5 分钟）
   2. 事后用 Claude Code 分析日志：
      "帮我分析这个 CPU 100% 的日志，找出可能的原因"
   3. 它帮你定位到问题代码
   4. 你修复后上线
```

---

### 8. 学习新技术时不该完全依赖它 📚

**错误做法：**
```bash
❌ 我想学 React，帮我写一个完整的 React 项目
   （然后你只是运行了一下，什么都没学会）
```

**Claude Code 是辅助学习的工具，不是替代品。**

**正确做法：**
```bash
✅ 自己先读文档，理解基本概念
✅ 让 Claude Code 给你写示例代码，你仔细研究
✅ 自己动手写一遍，加深理解
✅ 遇到不懂的，让 Claude Code 解释
```

**示例：学习 React Hooks**
```bash
❌ 错误：让 Claude Code 写 10 个 Hook 示例，你只是看了一遍

✅ 正确：
   1. 自己读 React 官方文档，理解 Hooks 的基本概念
   2. 让 Claude Code 写一个 useState 的示例
   3. 你自己动手改改看，观察状态变化
   4. 遇到不懂的，问 Claude Code："为什么这里要用 useState？"
   5. 自己写一个类似的组件，巩固理解
```

## ⚠️ 容易踩的坑（详细说明）

### 坑 1：无脑复制粘贴 📋

**危险场景：**
```bash
Claude Code："帮你写了一个数据库迁移脚本"
你："看起来不错" → 复制粘贴 → 运行 → 生产数据库被清空 💥
```

**它给的代码可能包含：**
```sql
-- 它给的 SQL 里可能有 DROP TABLE
DROP TABLE users;  -- 🚨 危险！

-- 它给的正则可能不匹配你的数据
const regex = /.*/;  -- 可能匹配过多

-- 它给的配置可能和你的环境冲突
listen 80;  -- 但你的 Nginx 已经配置了 80 端口
```

**正确做法：**
```bash
✅ 每一段代码都要看懂再执行
✅ 生产环境操作前，先备份
✅ 先在测试环境验证
✅ 重要操作要有人 review
```

---

### 坑 2：越改越大，停不下来 🌪️

**典型场景：**
```bash
你："帮我改一下这个函数"
Claude Code："改好了，但我发现这个函数依赖的那个模块也有问题，要不要一起改？"
你："好吧"
Claude Code："改好了，但那个模块的接口也需要调整..."
你："... 行吧"

3 小时后... 你原本只想改一个函数，现在改了 15 个文件。
```

**原来的小改动变成了大工程，然后越改越多，越改越乱。**

**正确做法：**
```bash
✅ 给 Claude Code 设定明确的范围
✅ 一次只做一件事
✅ 如果它提出"顺带"改其他东西，先评估是否必要
✅ 改完一个功能，就测试、提交、推送
```

**示例：**
```bash
❌ 错误："帮我优化一下用户模块"
   → 它会改用户、订单、支付... 所有相关模块

✅ 正确："帮我优化 `src/services/userService.ts` 里的 `getUserInfo` 函数"
   → 只改这个函数，范围明确
```

---

### 坑 3：失去手感，变成"AI 操作员" 🧟

**典型场景：**
```bash
连续用 Claude Code 写了一个月代码，
发现自己连基本的 for 循环语法都要想半天。
```

**这不是 Claude Code 的错，但你要有意识地保持手动编码的习惯。**

**正确做法：**
```bash
✅ 简单代码自己写，保持手感
✅ 复杂代码用 Claude Code 辅助
✅ 定期"离线编程"：不用 AI，自己写一些代码
✅ 用 Claude Code 学习新技术，而不是替代你思考
```

**建议的比例：**
| 代码类型 | 自己写 | Claude Code 辅助 |
|---------|--------|------------------|
| 简单逻辑（排序、过滤、循环） | 80% | 20% |
| 中等复杂度（组件、API 接口） | 40% | 60% |
| 高复杂度（架构设计、性能优化） | 20% | 80% |

---

### 坑 4：过度依赖搜索，失去思考能力 🤖

**典型场景：**
```bash
你："帮我看一下这个 npm 包怎么用"
Claude Code："用 xxx 就行"
你："帮我看一下这个 API 文档"
Claude Code："是这样的..."
你："帮我看一下这个报错什么意思"
Claude Code："意思是..."

一个月后... 你发现自己已经不会用 Google 了。
```

**偶尔搜索没问题，但如果每一行代码都要它帮你查——你在用它，还是它在替你思考？**

**正确做法：**
```bash
✅ 先自己查文档、搜 Google，培养解决问题的能力
✅ 实在解决不了，再让 Claude Code 帮你
✅ 让它帮你的时候，问清楚"为什么"，而不只是"怎么做"
✅ 把 Claude Code 当老师，而不是当搜索引擎
```

---

### 坑 5：盲目信任，不验证结果 ✅❌

**典型场景：**
```bash
Claude Code："帮你写了一个登录功能，已经测试过了，没问题"
你："好的" → 直接合并到 main 分支 → 上线 → 用户数据泄露 💥
```

**它说"已经测试过了" ≠ 真的测试过了。**

**正确做法：**
```bash
✅ 它给的任何代码，你都要自己测试
✅ 重要功能要写完整的单元测试
✅ 涉及安全的代码，要请安全专家 review
✅ 上线前要在测试环境验证
```

---

### 坑 6：在敏感项目中用，泄露公司代码 🔐

**危险场景：**
```bash
你把公司的核心业务代码粘贴到 Claude Code（云端版本）
→ 这些代码可能被用于训练模型
→ 可能被其他用户看到
→ 公司起诉你 💼
```

**正确做法：**
```bash
✅ 敏感项目、核心业务代码，不要用云端 AI 工具
✅ 用本地部署的 AI 工具（如果公司提供）
✅ 或者只用 AI 生成通用代码，不涉及业务逻辑
✅ 遵守公司的信息安全规定
```

## ✅ 该用的场景（对照一下）

| 场景 | 用还是不用 | 原因 |
|------|-----------|------|
| 创建新组件/页面 | ✅ 用 | 它 5 分钟，你半小时 |
| 修改现有功能的逻辑 | ⚠️ 用，但要自己 review | 它帮你写，你要把关 |
| 全局搜索替换 | ✅ 用，比编辑器更智能 | 它能理解语义，不只是文本匹配 |
| 写测试用例 | ✅ 用 | 枯燥的活儿交给它 |
| 调 Bug | ✅ 用，但最终修复你自己确认 | 它帮你定位，你做最终判断 |
| 代码 Review | ⚠️ 辅助用，不能替代人工 | 它做初筛，你做最终判断 |
| 写一行 console.log | ❌ 别用了 | 3 秒钟的事，别麻烦 AI |
| 修个拼写错误 | ❌ 别用了 | 同上 |
| 改个配置项 | ❌ 大多数情况别用了 | 编辑器的查找替换更快 |
| 生产环境操作 | ❌ 不用，自己来 | 生产环境容不得闪失 |
| 敏感数据操作 | ❌ 不用，自己来 | 数据安全是第一位的 |

## 📝 一个简单的判断流程

```
要做的任务
    │
    ├─ 明确目标吗？
    │   ├─ 不明确 → 先自己想清楚，不用
    │   └─ 明确 ↓
    │
    ├─ 自己做 < 3 分钟？
    │   ├─ 是 → 不用，自己做
    │   └─ 否 ↓
    │
    ├─ 涉及生产/敏感操作？
    │   ├─ 是 → 不用，自己来
    │   └─ 否 ↓
    │
    └─ 用 Claude Code！
```

---

## 🎓 学到了什么

1. **Claude Code 是效率工具，不是万能钥匙** — 合理使用才能发挥最大价值
2. **简单的事情自己做** — 启动成本高于执行成本时，别用它
3. **保持独立思考能力** — 它的建议要过脑子，不能无脑采纳
4. **了解边界才能信任** — 知道它什么时候会出错，才能放心让它在擅长的地方工作
5. **AI 是辅助，不是替代** — 你才是代码的负责人，AI 只是帮你提高效率
