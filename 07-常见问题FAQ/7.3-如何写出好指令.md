# 7.3 如何写出好指令？

> 垃圾进，垃圾出。指令写得烂，代码也不会好。

## 🎯 核心原则

好指令 = **做什么** + **什么风格** + **边界在哪**

缺一个，结果就可能跑偏。

---

## 💡 三要素公式

```
✅ 好指令 = 明确目标 + 上下文 + 约束条件

❌ 差指令 = "帮我写个页面"
```

---

## 📝 拆解：一份好指令长什么样（详细版）

### 要素 1：明确目标（要做什么）🎯

**差指令 ❌**
```
❌ 帮我写一个用户管理页面
```

**为什么差：**
- "用户管理页面" 太宽泛
- 不知道包含哪些功能
- 不知道用什么技术栈
- 不知道要做成什么样

**好指令 ✅**
```
✅ 创建一个用户管理页面，包含：
- 用户列表（表格展示，支持分页，每页 20 条）
- 搜索框（按用户名搜索）
- 新增用户按钮（点击弹出表单）
- 每行有编辑和删除操作
- 技术栈：React + TypeScript + Tailwind CSS
- 数据从 GET /api/users 获取
```

**为什么好：**
- 具体（列出了所有功能点）
- 可拆解（每个功能可以单独实现）
- 能验证（做完可以对照检查）

---

### 要素 2：提供上下文（现状是什么）📚

**差指令 ❌**
```
❌ 帮我改一下登录接口
```

**为什么差：**
- 哪个文件？
- 现在是什么实现？
- 要改成什么样？
- 用什么技术？

**好指令 ✅**
```
✅ 修改 src/api/auth.ts 中的 login 函数：
- 当前使用的是 session 认证
- 需要改成 JWT token 认证
- token 有效期 24 小时
- 使用 jsonwebtoken 库（已安装）
- 需要兼容现有的前端调用方式
- 错误返回格式保持 { error: string }
```

**为什么好：**
- 告诉它**现状是什么**（session 认证）
- 告诉它**要去哪里**（JWT token）
- 告诉它**用什么工具**（jsonwebtoken）
- 告诉它**有什么约束**（兼容前端、错误格式）

---

### 要素 3：设定约束（什么不能动）⚠️

**差指令 ❌**
```
❌ 帮我优化这个函数
```

**为什么差：**
- "优化"太宽泛（优化性能？可读性？）
- 没有约束，它可能过度优化
- 可能引入新依赖
- 可能改变函数签名

**好指令 ✅**
```
✅ 优化 src/utils/formatDate.ts 中的 formatDate 函数：
- 保持现有功能不变（输入输出不变）
- 不要引入新的依赖
- 优先考虑可读性，其次性能
- 需要通过现有的测试用例
- 目标：减少时间复杂度从 O(n²) 到 O(n)
```

**为什么好：**
- 明确**不能动的部分**（功能、签名、依赖）
- 明确**优化优先级**（可读性 > 性能）
- 明确**验收标准**（通过测试用例）
- 明确**优化目标**（复杂度从 O(n²) 到 O(n)）

## 🔧 实战：指令对比（更多案例）

### 案例 1：创建 API 🌐

**差指令 ❌**
```
❌ 帮我写一个用户 API
```

**问题：**
- 不知道要哪些接口
- 不知道用什么框架
- 不知道数据格式
- 不知道错误处理方式

**好指令 ✅**
```
✅ 在 Express 项目中创建用户相关 API：
文件路径：src/routes/user.ts

包含以下接口：
  GET    /api/users       - 获取用户列表，支持 ?page=1&limit=20&search=xxx
  GET    /api/users/:id   - 获取单个用户详情
  POST   /api/users       - 创建用户（需要 name, email, password）
  PUT    /api/users/:id   - 更新用户信息
  DELETE /api/users/:id   - 删除用户

技术要求：
- 使用 TypeScript
- 使用 Prisma ORM 操作数据库
- 统一响应格式 { success, data, error }
- 错误处理用 try-catch
- 参数验证用 zod（已安装）
- 密码用 bcrypt 哈希
- POST 和 PUT 需要 JWT 认证
```

**为什么好：**
- 列出了所有接口（路径、方法、参数）
- 指定了技术栈（Express + TypeScript + Prisma + zod）
- 指定了响应格式和错误处理
- 指定了认证方式

---

### 案例 2：修复 Bug 🐛

**差指令 ❌**
```
❌ 这个函数有 bug，帮我修一下
```

**问题：**
- 哪个函数？
- 什么 bug？
- 怎么复现？
- 期望行为是什么？

**好指令 ✅**
```
✅ src/services/orderService.ts 的 calculateTotal 函数有 bug：

问题描述：
- 当购物车为空时返回 NaN 而不是 0
- 当商品价格为负数时没有校验

复现步骤：
1. 创建空购物车
2. 调用 calculateTotal()
3. 返回 NaN（期望 0）

修复要求：
- 空购物车返回 0
- 负价格抛出错误 "Invalid price"
- 不要改变现有的正常计算逻辑
- 加上对应的单元测试
- 测试文件：src/services/__tests__/orderService.test.ts
```

**为什么好：**
- 明确指出文件和函数
- 描述了 bug 的具体表现
- 给出了复现步骤
- 说明了期望行为
- 指定了修复要求（不改变正常逻辑）
- 要求写测试

---

### 案例 3：重构代码 🔄

**差指令 ❌**
```
❌ 这段代码太乱了，帮我重构
```

**问题：**
- "太乱了"是主观判断
- 不知道要怎么重构
- 不知道要拆分还是优化
- 可能改完发现不是你想要的样子

**好指令 ✅**
```
✅ 重构 src/components/UserProfile.tsx：

问题：
1. 组件超过 300 行，需要拆分
2. 有重复的格式化逻辑（日期、金额）
3. 缺少错误状态处理

要求：
- 拆分成 UserProfile（主组件）+ UserAvatar + UserInfo 三个组件
- 提取公共的格式化函数到 src/utils/format.ts
- 添加 loading 和 error 状态
- 保持现有样式不变（Tailwind 类名不动）
- 每个子组件单独导出
- 写单元测试覆盖新组件
```

**为什么好：**
- 指出了具体问题（行数、重复代码、缺少状态）
- 给出了重构方案（拆分成哪几个组件）
- 指定了提取工具函数到哪里
- 指定了约束（样式不变、单独导出）
- 要求写测试

---

### 案例 4：性能优化 ⚡

**差指令 ❌**
```
❌ 帮我优化一下性能
```

**好指令 ✅**
```
✅ 优化 src/pages/UserList.tsx 的渲染性能：

问题：
- 用户列表超过 500 条时，滚动卡顿
- 每次父组件更新，所有子组件都重新渲染

优化方案：
- 用 React.memo 包裹 UserRow 组件
- 用 useMemo 缓存计算逻辑（过滤、排序）
- 用 useCallback 缓存回调函数
- 考虑虚拟滚动（react-window）
- 保持功能不变

验收标准：
- 500 条数据滚动流畅（60 FPS）
- React DevTools Profiler 显示避免不必要渲染
- 所有现有测试通过
```

---

### 案例 5：添加功能 ➕

**差指令 ❌**
```
❌ 帮我加个导出功能
```

**好指令 ✅**
```
✅ 给 src/pages/UserList.tsx 添加导出功能：

功能要求：
- 点击"导出"按钮，导出当前列表数据为 CSV
- 导出文件名：users_YYYYMMDD_HHMMSS.csv
- 导出字段：姓名、邮箱、电话、创建时间
- 支持中文（UTF-8 with BOM）

实现要求：
- 纯前端导出（不调接口）
- 用 Blob 和 URL.createObjectURL 实现
- 导出时在按钮显示"导出中..."，禁用按钮
- 导出完成后显示"导出成功"提示（3 秒后消失）
- 不添加依赖库（自己实现）
```

## 🧩 不同任务的最佳指令模板（详细版）

### 1. 创建新功能 🆕

**模板：**
```
创建 [功能名称]，包含以下功能点：
1. [功能点 1：详细描述]
2. [功能点 2：详细描述]
3. [功能点 3：详细描述]

技术要求：
- 文件路径：[路径]
- 使用 [技术/库]
- 遵循 [项目规范]
- 需要/不需要测试
- 需要/不需要文档

样式要求：
- [如果有 UI，描述样式要求]

验收标准：
- [列出验收条件]
```

**完整示例：**
```
创建用户注册功能，包含以下功能点：
1. 注册表单（用户名、邮箱、密码、确认密码）
2. 表单验证（邮箱格式、密码强度、两次密码一致）
3. 提交后调用 POST /api/register
4. 注册成功跳转到登录页
5. 注册失败显示错误提示

技术要求：
- 文件路径：src/pages/Register.tsx
- 使用 React + TypeScript + Formik + Yup
- 遵循项目现有代码规范（ESLint + Prettier）
- 需要单元测试（覆盖验证逻辑）
- 需要集成测试（mock API 调用）

样式要求：
- 用 Tailwind CSS
- 参考 src/pages/Login.tsx 的样式

验收标准：
- 所有表单验证通过才能提交
- 提交时显示 loading 状态
- 注册成功显示"注册成功，3 秒后跳转到登录页"
- 注册失败显示错误信息
- 测试覆盖率 > 80%
```

---

### 2. 修改现有代码 ✏️

**模板：**
```
修改 [文件路径] 中的 [函数/组件名称]：

当前行为：[描述现状]
期望行为：[描述目标]

修改原因：[为什么改]

约束：
- 不要修改 [不该动的部分]
- 保持向后兼容 / 可以破坏性变更
- 使用 [指定的方式]
- 需要/不需要迁移脚本
```

**完整示例：**
```
修改 src/api/auth.ts 中的 login 函数：

当前行为：
- 使用 session + cookie 认证
- 登录成功后设置 session.user_id
- 返回 { success: true }

期望行为：
- 改成 JWT token 认证
- 登录成功后返回 { token, user }
- token 有效期 7 天
- 使用 jsonwebtoken 库（已安装）

修改原因：
- 要支持移动端（session 不适用）
- 要支持单点登录（SSO）

约束：
- 不要修改前端调用方式（还是 POST /api/login）
- 保持向后兼容（旧版本 app 还能用 session）
- 使用 Bearer token 格式
- 需要写迁移指南（告诉前端怎么改）
```

---

### 3. 调试 Bug 🐞

**模板：**
```
[文件路径] 出现 [错误信息]：

复现步骤：
1. [步骤 1]
2. [步骤 2]

期望结果：[正确结果]
实际结果：[错误结果]

已尝试：[你做过什么]
相关代码：[贴出关键代码片段]
环境信息：[Node 版本、库版本等]
```

**完整示例：**
```
src/services/userService.ts 出现 TypeError: Cannot read property 'map' of undefined：

复现步骤：
1. 打开用户列表页
2. 点击"刷新"按钮
3. 控制台报错

期望结果：显示用户列表
实际结果：白屏，控制台报错

已尝试：
- 检查网络请求，接口返回 200，数据正常
- 打印 response.data，是 undefined

相关代码：
```typescript
// src/services/userService.ts
getUsers(): Promise<User[]> {
  return api.get('/users').then(response => response.data.map(u => u));
}
```

环境信息：
- axios 版本：0.27.2
- API 返回格式：{ success: boolean, data: User[] }
```

## ⚡ 高级技巧

### 技巧 1：分步指令（大任务拆小）🪜

大任务不要一次性扔给它，拆成小步骤：

```
第一步：先帮我设计数据库表结构，我要你确认后再写代码
```

等它回复确认后：

```
好的，按这个结构生成 Prisma schema
```

再下一步：

```
基于这个 schema，创建 CRUD API
```

**为什么有效：**
- 每一步都可以验证
- 出错时容易定位
- 不会因为一次性输入太多而跑偏

---

### 技巧 2：提供示例（参照物）🖼️

```
帮我创建一个和 src/components/UserCard 类似风格的 ProductCard 组件
```

有参照物，风格就不会跑偏。

**更好的做法：**
```
帮我创建一个 ProductCard 组件，参考以下风格：
- 卡片布局：图片 + 标题 + 描述 + 操作按钮
- 样式：用 Tailwind CSS，圆角 8px，阴影 md
- 交互：hover 时阴影变成 lg，有过渡动画
- 参考文件：src/components/UserCard.tsx
```

---

### 技巧 3：先让它思考（避免盲目写代码）🤔

```
我要重构这个模块，先帮我分析一下有哪些方式，
列出每种方式的优缺点，不要直接写代码
```

让它先给方案，你选一个再让它实现。

**完整示例：**
```
分析 src/modules/user 的重构方向：

当前问题：
1. 文件超过 1000 行
2. 有重复的业务逻辑
3. 缺少错误处理

请列出 3 种重构方案，说明：
- 每种方案的优点
- 每种方案的缺点
- 预计工作量
- 风险点

不要写代码，只列方案。
```

[它列出 3 种方案]

```
我选方案 2，按这个方案实现重构，保持 API 兼容
```

### 技巧 4：设定角色（聚焦输出）🎭

```
你是一个有 5 年经验的 React 开发者，
擅长性能优化和无障碍设计。
帮我 review 一下这个组件。
```

角色设定能让输出更聚焦。

**更多角色示例：**
```
# 角色 1：代码审查专家
你是一个严格的技术 leader，
关注代码质量、性能、安全性。
帮我 review 这个 PR。

# 角色 2：TypeScript 专家
你是 TypeScript 类型体操高手，
帮我优化这些类型定义，
要求类型安全、可读性好。

# 角色 3：测试专家
你是测试驱动开发（TDD）的忠实粉丝，
帮我为这个函数写完整的单元测试，
覆盖正常、异常、边界情况。
```

### 技巧 5：使用负面指令（告诉它不要什么）🚫

```
创建用户管理 API，
但不要：
- 不要使用 any 类型
- 不要引入新的依赖
- 不要改变现有的错误处理机制
- 不要删除已有的注释
```

负面指令和正面指令一样重要。

---

### 技巧 6：提供参考链接或文档 🔗

```
实现 OAuth2.0 登录，
参考这个文档：https://tools.ietf.org/html/rfc6749

重点实现：
- Authorization Code Flow
- PKCE 扩展
```

有文档参考，它就不会"自由发挥"。

## ❌ 常见错误

| 错误 | 问题 | 修正 |
|------|------|------|
| "帮我改一下" | 改什么？怎么改？ | 说清文件、位置、期望结果 |
| "像淘宝那样" | 太模糊 | 截图或详细描述具体功能 |
| "代码优化一下" | 优化什么？性能？可读性？ | 明确优化维度和指标 |
| 一次给 10 个任务 | 信息过载 | 每次一个任务 |
| 不给上下文直接贴代码 | 它不知道前后关系 | 说清文件位置、技术栈、已有代码 |
| 用模糊的代词 | "它"、"那个"指什么？ | 用具体的文件名、函数名、变量名 |

---

## 🎓 学到了什么

1. **好指令 = 目标 + 上下文 + 约束**，缺一不可
2. **越具体越好**，模糊是效率的敌人
3. **大任务拆小步**，每一步都确认再往下走
4. **提供参照物**，风格和结构就不会跑偏
5. **先让它思考，再让它写代码**，避免返工
6. **使用负面指令**，告诉它不要做什么，和告诉它做什么一样重要

---

## ⚠️ 注意

- 不要指望一次指令就完美，好的结果往往需要 2-3 轮对话
- 指令写不好不是你笨，是经验不够——多写几次就有感觉了
- 如果你发现自己反复说同样的要求，把它写进 `instructions.md`
- 指令的长度不是关键，**清晰度才是**。有时候 50 个字就能说清楚，不需要写 500 个字
