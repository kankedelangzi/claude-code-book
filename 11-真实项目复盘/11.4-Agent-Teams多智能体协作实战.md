# 11.4 Agent Teams 多智能体协作实战

> **案例背景**：2026 年 5 月，Claude Code 推出 Agent Teams（多智能体协作）功能，多个 AI 实例可以在同一个项目中协同工作。本案例展示如何用 Agent Teams 在 30 分钟内交付一个带用户认证的完整博客系统（真实案例来自字节某团队）。

---

## 什么是 Agent Teams？

传统的 Subagents 模式是"主代理 → 子代理"的**单向委派**：主对话将任务分给子代理，子代理执行后返回结果。

**Agent Teams 突破了这一边界**：多个 AI 实例在同一个项目中协同工作，它们可以：
- ✅ **互相通信**：点对点直接发消息，不再通过主代理中转
- ✅ **共享任务进度**：看板式的任务列表（pending → in_progress → completed）
- ✅ **对抗式验证**：质疑对方的结论，通过讨论提高代码质量
- ✅ **独立上下文**：每个智能体有独立的上下文窗口，避免混乱

### 核心角色

| 角色 | 职责 |
|------|------|
| **Team Lead（团队负责人）** | 拆解任务、创建队友、协调进度、汇总结果 |
| **Teammates（队友智能体）** | 各自独立运行，可直接交换信息、质疑对方结论 |

## 真实案例：30 分钟交付博客系统

**案例来源**：字节某团队（2026 年 5 月）

**传统做法**：
- 搭建前后端框架：2-3 小时
- 实现用户认证（JWT + Redis）：4-6 小时
- 博客 CRUD + 富文本编辑器：3-4 小时
- 部署到云服务：1-2 小时
- **总计**：10-15 小时（2 个工作日）

**Agent Teams 做法**：
- ✅ **30 分钟**交付完整博客系统
- ✅ 包含用户认证、博客 CRUD、评论系统、部署脚本
- ✅ 3 个 Agent 并行工作（前端、后端、部署）

### 实战步骤

#### 第一步：创建 Agent Team

在 Claude Code 中输入：

```
创建 Agent Team，3 个队员，任务：开发一个带用户认证的博客系统

技术栈：
- 前端：Next.js 14 + TypeScript + Tailwind CSS
- 后端：Node.js + Express + Prisma + PostgreSQL
- 认证：JWT + bcrypt
- 部署：Docker Compose

队员分工：
1. 前端 Agent：负责页面组件、路由、API 调用
2. 后端 Agent：负责 API 接口、数据库模型、认证逻辑
3. 部署 Agent：负责 Dockerfile、docker-compose.yml、环境变量配置

请拆解为具体任务清单，分配给各队员。
```

**Claude Code 会生成**：

```

Team Lead: claude-lead-001
Teammates: 
  - claude-frontend-001 (前端 Agent)

  - claude-deploy-001 (部署 Agent)

任务清单：
[T1] 设计数据库模型 (backend)
[T2] 创建 Prisma Schema (backend)
[T3] 实现用户注册 API (backend)

#### 第三步：Agent 之间的协作

**场景**：前端 Agent 需要后端 API 接口文档

```
# 前端 Agent 给后端 Agent 发消息
claude-frontend-001> @claude-backend-001 
  我需要实现博客列表页，请提供：
  1. GET /api/posts 接口的参数说明
  2. 响应数据的 TypeScript 类型定义
  
# 后端 Agent 收到消息，自动回复
claude-backend-001> @claude-frontend-001
  接口文档已生成：
  
  GET /api/posts?page=1&limit=10
  响应类型：
  interface Post {
    id: string;
    title: string;
    content: string;
    author: { name: string; avatar: string };
    createdAt: string;
  }
  
  已写入 docs/api.md，你可以直接导入类型定义。
```

**场景**：后端 Agent 发现数据库模型需要修改

```
claude-backend-001> @claude-lead-001
  我发现需要给 Post 模型添加 'published' 字段（草稿/发布），
  建议修改 Prisma Schema，是否同意？
  
claude-lead-001> @claude-backend-001 同意，请修改，并通知 frontend 更新类型定义。
  
claude-backend-001> @claude-frontend-001
  Prisma Schema 已更新，请重新导入类型定义：
  npx prisma generate
```

#### 第四步：审查与合并

当所有 Agent 完成后，Team Lead 会自动汇总结果：

```

  - 创建 12 个 API 接口

⚠️ 需要人工审查：
  1. 检查 JWT 密钥是否安全（建议用 openssl rand -hex 32 生成）

## 最佳实践：5 个文件夹让 Claude Code 变身完整开发团队

根据社区经验（来源：博客园），用以下 5 个文件夹组织项目，可以让 Claude Code 变成**完整的开发团队**：

```
my-project/
├── .claude/
│   ├── commands/       # 自定义指令（可复用的工作流）
│   ├── hooks/          # 安全护栏（自动触发脚本）
│   ├── subagents/      # 隔离式子智能体集群
│   ├── plugins/        # 一键标准化分发中心
│   └── settings.json   # 项目配置文件
```

### 1. commands/：自定义指令

存放可复用的工作流，例如：

```bash
# .claude/commands/code-review.md
Review the changes in the current branch:
1. Run `git diff main...HEAD`
2. Look for:
   - Logic errors
   - Security issues (SQL injection, XSS, etc.)
   - Performance problems
   - Missing edge cases
3. Suggest specific improvements with code examples
4. Rate the code quality from 1-10
```

使用方式：

```bash
/code-review
```

### 2. hooks/：项目安全与质量护栏

存放 shell 脚本，在**每次工具调用前后自动触发执行**。

例如，拦截危险命令：

```bash
# .claude/hooks/pre-bash.sh
#!/bin/bash
COMMAND="$1"

if [[ $COMMAND == *"rm -rf"* ]] || [[ $COMMAND == *"DROP DATABASE"* ]]; then
  echo "⚠️ 危险命令被拦截: $COMMAND"
  echo "如需执行，请手动运行。"
  exit 1
fi
```

### 3. subagents/：隔离式子智能体集群

用于搭建多个相互隔离的 AI 子智能体，每个子智能体拥有独立的上下文权限。

```
subagents/
├── code-reviewer/    # 代码审查子智能体
├── test-runner/      # 测试运行子智能体
├── doc-writer/       # 文档编写子智能体
└── security-checker/ # 安全检查子智能体
```

**示例**：创建代码审查子智能体

```bash
# 在 Claude Code 中输入：
创建子智能体：code-reviewer
职责：审查代码漏洞、检查代码风格、提出改进建议
触发时机：每次 git commit 前自动运行
```

### 4. plugins/：一键标准化分发中心

支持所有自定义技能、规则、子智能体配置的**一键打包与团队分发**。

```bash
# 打包当前项目的 Claude Code 配置
claude plugins pack my-config

# 分享给团队成员
# 他们只需运行：
claude plugins install my-config.tar.gz
```

### 5. settings.json：项目配置

配置项目级别的规则和模型偏好。

```json
{
  "model": "claude-opus-4.5",
  "permissions": {
    "allow": ["Bash(npm test)", "Bash(git status)"],
    "deny": ["Bash(rm -rf *)", "Bash(DROP DATABASE *)"]
  },
  "rules": [
    "所有 API 接口必须有错误处理",
    "所有函数必须有 JSDoc 注释",
    "不要使用 any 类型"
  ]
}
```

## 注意事项与最佳实践

### ✅ 适合用 Agent Teams 的场景

1. **大型项目**：多个模块可以并行开发
2. **代码审查**：多个 PR 可以同时审查
3. **测试编写**：为每个模块生成测试用例
4. **文档生成**：API 文档、README、变更日志

### ❌ 不适合用 Agent Teams 的场景

1. **小型项目**：开销大于收益
2. **强依赖顺序的任务**：Agent 之间需要频繁通信，反而降低效率
3. **需要精细控制的任务**：Agent 可能会"自由发挥"，偏离你的预期

### 💡 最佳实践

1. **明确分工**：在创建 Team 时，清晰地定义每个 Agent 的职责
2. **设置检查点**：让 Lead Agent 定期检查各 Agent 的进度
3. **人工审查**：Agent 完成后，一定要人工审查关键代码（认证、支付、数据处理）
4. **控制数量**：一般 3-5 个 Agent 最佳，过多会导致通信开销增大
5. **使用 Agent View**：实时监控进度，及时发现问题
