# 11.4 Agent Teams 多智能体协作实战

> **案例背景**：2026 年 5 月，Claude Code 推出实验性功能 Agent Teams（多智能体协作），多个 AI 实例可以在同一个项目中协同工作。本案例展示 Agent Teams 的核心原理、配置方法和实战场景，帮助你在 30 分钟内用多智能体团队交付一个带用户认证的完整博客系统。

---

## 什么是 Agent Teams？

传统的 Subagents 模式是"主代理 → 子代理"的**单向委派**：主对话将任务分给子代理，子代理执行后返回结果。

**Agent Teams 突破了这一边界**：多个 AI 实例在同一个项目中协同工作，它们可以：
- ✅ **互相通信**：点对点直接发消息，不再通过主代理中转
- ✅ **共享任务进度**：看板式的任务列表（pending → in_progress → completed）
- ✅ **对抗式验证**：质疑对方的结论，通过讨论提高代码质量
- ✅ **独立上下文**：每个智能体有独立的上下文窗口，避免混乱

### 核心组件

```
┌─────────────────────────────────────────────────────────┐
│                  Team Lead（团队负责人）                   │
│         拆解任务 / 创建队友 / 协调进度 / 汇总结果          │
│                                                         │
│   ┌──────────┐    ┌───────────┐    ┌────────────┐      │
│   │ 队友 A   │←──→│ 队友 B    │←──→│ 队友 C     │      │
│   │独立上下文 │    │独立上下文  │    │独立上下文   │      │
│   └─────┬────┘    └─────┬─────┘    └─────┬──────┘      │
│         │               │                │              │
│         └───────────────┼────────────────┘              │
│                         ↓                               │
│              共享任务列表（Task List）                     │
│            pending → in_progress → completed             │
└─────────────────────────────────────────────────────────┘
                        ↑↓
              Mailbox（消息系统）
           定向消息 / 广播消息 / 空闲通知
```

| 组件 | 职责 |
|------|------|
| **Team Lead（团队负责人）** | 拆解任务、创建队友、监控进度、汇总结果 |
| **Teammates（队友智能体）** | 独立运行的 Claude 实例，拥有独立上下文窗口，可以与其他队友直接通信 |
| **Task List（共享任务列表）** | 所有智能体共享的任务看板，每个任务有三种状态：pending → in_progress → completed |
| **Mailbox（消息系统）** | 智能体之间的通信通道，支持定向消息和广播消息，消息即时送达 |

## ⚠️ 前置条件与启用方式

Agent Teams 目前仍是**实验性功能**，需要手动启用。

### 版本要求

- Claude Code 版本不低于 **2.1.32**
- 推荐搭配 **Opus 4.6** 或 **Sonnet** 模型使用

```bash
# 检查版本
claude --version

# 更新到最新版
claude update
```

### 启用方式

**方式一：编辑 settings.json（推荐，永久生效）**

编辑 `~/.claude/settings.json`：

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

保存后重启 Claude Code 使配置生效。

**方式二：环境变量（临时生效，适合快速测试）**

```bash
export CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1
claude
```

### 显示模式

Agent Teams 提供两种显示模式：

| 模式 | 说明 | 适用场景 |
|------|------|---------|
| **进程内模式**（In-Process） | 所有队友运行在同一个终端中，通过快捷键切换 | 任何终端环境 |
| **分屏模式**（Split-Pane） | 每个队友有独立终端窗格，可同时看到所有输出 | 需 tmux 或 iTerm2 |

默认模式为 `auto`：检测到 tmux 环境时自动使用分屏模式，否则使用进程内模式。

```bash
# 手动指定模式
claude --teammate-mode in-process
claude --teammate-mode tmux
```

### 安装 tmux（分屏模式需要）

```bash
# macOS
brew install tmux

# Ubuntu / Debian / WSL
sudo apt update && sudo apt install tmux
```

## 三种并行工作方案对比

Claude Code 提供了三种并行工作方案，适用场景各不相同：

| 维度 | Subagents（子代理） | Agent Teams（团队模式） | Worktree（工作树） |
|------|---------------------|------------------------|-------------------|
| **拓扑结构** | 星型：主对话居中，子代理汇报 | 网状：队友之间直接通信 | 无拓扑：完全独立的会话 |
| **上下文** | 各自独立窗口，结果摘要返回主对话 | 各自独立窗口，完全自主运行 | 各自独立窗口，独立 Git 分支 |
| **通信方式** | 子代理只能向主对话汇报 | 队友之间可以直接互发消息 | 无自动通信，需手动协调 |
| **协调方式** | 主对话统一调度 | 共享任务列表 + 自主认领 | 完全手动 |
| **并发安全** | 单会话内安全 | 文件锁防冲突 | Git 分支隔离 |
| **Token 成本** | 较低 | 较高（约 3-4 倍） | 低（无协调通信开销） |
| **适用场景** | 专注型任务，只需要结果 | 复杂任务，需要讨论和协作 | 长期并行的独立功能开发 |

**选型建议**：
- 子任务独立、只需执行和返回结果 → **Subagents**
- 任务复杂、需要多角度讨论和跨角色协作 → **Agent Teams**
- 需要队友之间相互校验和挑战 → **Agent Teams**
- 独立功能分支、长期并行开发 → **Worktree**
- 控制成本优先 → **Subagents**

## 实战案例：多智能体团队交付博客系统

**传统做法**：
- 搭建前后端框架：2-3 小时
- 实现用户认证（JWT + Redis）：4-6 小时
- 博客 CRUD + 富文本编辑器：3-4 小时
- 部署到云服务：1-2 小时
- **总计**：10-15 小时（2 个工作日）

**Agent Teams 做法**：
- ✅ 3-5 个 Agent 并行工作（前端、后端、测试）
- ✅ 包含用户认证、博客 CRUD、评论系统
- ✅ 核心框架搭建仅需几十秒到几分钟

### 实战步骤

#### 第一步：创建 Agent Team

确保已启用实验性功能后，在 Claude Code 中输入：

```
创建一个智能体团队来开发带用户认证的博客系统，包含 3 个队友：
- 队友 1（后端）：设计数据库模型、实现 API 接口和 JWT 认证
- 队友 2（前端）：实现页面组件、路由和 API 调用
- 队友 3（测试）：编写端到端集成测试

技术栈：
- 前端：Next.js 14 + TypeScript + Tailwind CSS
- 后端：Node.js + Express + Prisma + PostgreSQL
- 认证：JWT + bcrypt

将工作分解为可以独立完成的并行任务。
```

**Claude Code 会生成**：

```
✅ Agent Team 创建成功！

Team Lead: 当前会话
Teammates:
  - 队友1 (后端)
  - 队友2 (前端)
  - 队友3 (测试)

任务清单：
[T1] 设计数据库模型 (后端)
[T2] 创建 Prisma Schema (后端)
[T3] 实现用户注册/登录 API + JWT (后端)
[T4] 创建博客 Post CRUD API (后端)
[T5] 设计首页 UI (前端)
[T6] 实现博客列表/详情页 (前端)
[T7] 实现登录/注册页面 (前端)
[T8] 编写端到端集成测试 (测试)

依赖关系：T5/T6 等待 T2 完成；T8 等待 T3/T4/T7 完成
```

#### 第二步：监控并行开发

```bash
# 进程内模式快捷键
Shift+Up/Down    # 切换选中的队友
Enter            # 进入该队友的会话视图
Escape           # 返回 Team Lead 视图
Ctrl+T           # 显示/隐藏任务列表

# 分屏模式（tmux）
# 点击对应窗格即可切换到该队友
```

#### 第三步：Agent 之间的协作

**场景**：前端队友需要后端 API 接口文档

```
# 前端队友给后端队友发定向消息
> @队友1 我需要实现博客列表页，请提供 GET /api/posts 接口的参数和响应类型

# 后端队友收到消息，自动回复
> @队友2 接口文档已生成：
> GET /api/posts?page=1&limit=10
> 响应类型已写入 docs/api.md
```

**场景**：后端队友修改了数据库模型

```
# 后端队友广播通知
> @all Prisma Schema 已更新，添加了 Post.published 字段，请重新生成类型：
> npx prisma generate
```

#### 第四步：审查与合并

当所有队友完成后，Team Lead 会自动汇总结果：

```
所有任务已完成，正在汇总...

✅ 后端队友完成：数据库模型、12 个 API 接口、JWT 认证中间件
✅ 前端队友完成：8 个页面组件、API 调用逻辑、样式
✅ 测试队友完成：端到端集成测试、API 测试

⚠️ 需要人工审查：
1. JWT 密钥安全性（建议用 openssl rand -hex 32 生成）
2. Docker 端口映射是否冲突
3. 手动测试登录流程

是否自动提交到 Git？（y/n）
```

## 高级控制

### 委托模式（Delegate Mode）

默认情况下，Team Lead 可能会自己动手写代码。如果你希望它只负责协调和调度，可以开启委托模式：

```bash
# 快捷键切换
Shift+Tab
```

在委托模式下，Team Lead 只做协调工作，不会修改代码或执行命令。

### 计划审批（Plan Approval）

对于复杂或高风险的任务，可以要求队友在动手之前先提交执行计划，由 Team Lead 审批通过后再开始实施：

```
> 创建团队时，要求所有队友在执行前先提交计划，等审批通过后再动手。
```

在计划审批模式下，队友只能读取文件和调查信息，无法修改代码。

### 指定队友模型

默认队友使用与 Team Lead 相同的模型。你可以针对不同任务指定不同模型：

```
创建一个包含 4 个队友的团队：
- 1 个使用 Haiku 的研究员，负责快速检索和信息收集
- 1 个使用 Opus 的架构师，负责复杂的设计决策
- 2 个使用 Sonnet 的实现者，负责代码编写和测试
```

### 预批准权限

队友执行文件操作或命令时会向 Team Lead 请求权限确认。在大型团队中，频繁的权限请求会成为瓶颈：

```bash
# 创建团队前预批准常用操作
/permissions
```

### 关闭队友与清理团队

```
# 关闭单个队友
> 关闭队友 xxx

# 清理整个团队
> 清理团队（需先关闭所有活跃队友）
```

## 通过 Hooks 把控质量

Hooks 可以作为质量关卡，在队友完成工作的关键节点进行自动化检查：

- **TeammateIdle**：队友完成任务进入空闲状态时触发。如果检查脚本发现问题，返回 `exit 2` 并附上反馈信息，队友会收到反馈并继续工作。
- **TaskCompleted**：任务即将标记为完成时触发。返回 `exit 2` 可以阻止任务完成，将修改意见返回给队友。

示例配置：

```json
{
  "hooks": {
    "TaskCompleted": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "./scripts/verify-task-quality.sh"
          }
        ]
      }
    ]
  }
}
```

## 五大实战场景

### 场景1：多视角并行代码审查

让多个队友从不同角度同时分析同一套代码：

```
创建一个智能体团队来审查 PR #142，包含三个审查员：
- 安全专家：检查注入风险、认证缺陷、敏感信息暴露
- 性能分析师：查找 N+1 查询、内存泄漏、不必要的循环
- 测试验证者：检查边界情况覆盖和测试充分性

各自独立完成审查后，由 Team Lead 汇总为按优先级排序的问题清单。
```

### 场景2：对抗式调试

当问题的根本原因不明确时，让多个智能体同时验证不同假设：

```
用户报告结账接口出现间歇性 500 错误，约 5% 的请求会失败，无明显规律。

创建 5 个调查员分别验证以下假设：
1. 数据库连接池耗尽
2. 库存竞态条件
3. 第三方支付超时
4. 内存 GC 问题
5. 网络抖动

要求：每个调查员必须给出支持或否定其假设的具体证据；
调查员之间互相挑战、质疑对方的结论。
```

### 场景3：跨层功能开发

将一个完整的功能拆分为互不干扰的层级：

```
创建一个智能体团队来开发通知系统，包含以下队友：
- 队友 1（后端）：设计并实现通知 API
- 队友 2（数据库）：设计表结构、编写迁移脚本
- 队友 3（前端）：实现通知铃铛组件、通知列表页
- 队友 4（实时）：WebSocket 集成，实现实时推送
- 队友 5（测试）：编写端到端集成测试

任务依赖明确，每个队友只修改自己负责范围内的文件。
```

### 场景4：技术方案竞标评审

让不同队友分别论证不同方案：

```
我们需要为项目选择状态管理方案。创建一个评审团队：
- 队友 A（Redux 方案）：论证使用 Redux Toolkit 的优势
- 队友 B（Zustand 方案）：论证使用 Zustand 的优势
- 队友 C（Pinia 方案）：论证使用 Pinia 的优势

每个队友必须给出基于当前项目的实际论证，并列出缺点和风险。
队友之间互相质疑对方方案的薄弱点，Team Lead 最终输出对比分析报告。
```

### 场景5：大规模代码迁移

当需要在大量文件中执行统一变更时：

```
项目需要将所有 API 请求从 axios 迁移到原生 fetch，涉及约 60 个文件。
创建一个迁移团队，按目录分工，队友 4 在所有迁移完成后更新测试文件。
```

## 最佳实践

### ✅ 适合用 Agent Teams 的场景

1. **跨层全栈开发**：多个模块可以并行开发
2. **多维度代码审查**：从安全、性能、测试等不同角度同时审查
3. **对抗式调试**：多个假设并行验证，互相证伪
4. **技术方案评审**：多个方案并行论证，互相挑战
5. **大规模代码迁移**：按目录分工，并行修改

### ❌ 不适合用 Agent Teams 的场景

1. **任务严格串行**：无法并行，协调成本大于收益
2. **频繁修改同一文件**：多队友修改同一文件易产生冲突
3. **任务间强耦合**：队友之间需要频繁等待
4. **简单的日常任务**：单会话或 Subagents 更经济

### 💡 最佳实践

1. **明确分工**：每个队友操作不同的文件或目录，避免冲突
2. **给队友足够的上下文**：启动提示应包含任务目标、文件范围、技术约束、期望产出
3. **任务粒度适中**：建议每个队友分配 5-6 个任务
4. **模型分层**：研究任务用 Haiku，编码用 Sonnet，架构用 Opus
5. **控制团队规模**：3-5 个队友最佳，过多导致通信开销增大
6. **及时关闭空闲队友**：减少 Token 消耗
7. **人工审查**：完成后一定要人工审查关键代码（认证、支付、数据处理）
8. **先单会话评估**：确认复杂度确实需要多智能体协作后再启用

## 当前限制与注意事项

| 限制 | 说明 | 应对方式 |
|------|------|---------|
| 不支持会话恢复 | `/resume` 和 `/rewind` 不会恢复进程内模式下的队友 | 在关键节点手动保存进展 |
| 任务状态偶尔不同步 | 队友有时不会及时将任务标记为 completed | 通过 `Ctrl+T` 手动检查并干预 |
| 关闭存在延迟 | 队友会在完成当前请求后才退出 | 预留等待时间，不要立即清理 |
| 单会话单团队 | 一个 Team Lead 同一时间只能管理一个团队 | 如需多个团队，使用多个终端会话 |
| 不支持嵌套团队 | 队友无法创建或管理子团队 | 通过 Team Lead 统一协调所有队友 |
| Token 成本线性增长 | 每个队友都是独立 Claude 实例 | 控制团队规模，及时关闭空闲队友 |
| 文件冲突风险 | 多个队友修改同一文件可能产生冲突 | 严格划分文件范围，避免交叉操作 |
| 对话历史不继承 | 队友不会自动继承 Team Lead 的对话历史 | 将关键信息写入 CLAUDE.md |

> ⚠️ **版本要求**：Agent Teams 需要 Claude Code v2.1.32+，推荐搭配 Opus 4.6 或 Sonnet 模型。作为实验性功能，在会话恢复、异常关闭等场景存在已知局限性，重要项目请及时保存代码与配置。

## 小结

Agent Teams 是 Claude Code 在 2026 年最重要的更新之一，它让"多个 AI 协同工作"成为现实。

**核心要点**：
1. Agent Teams = 多个 AI 实例协同工作 + 点对点通信 + 共享任务进度
2. **实验性功能**，需要在 settings.json 中手动启用
3. 与 Subagents 本质区别：网状通信 vs 星型通信，自主协作 vs 被动执行
4. 五大实战场景：代码审查、对抗式调试、跨层开发、方案评审、代码迁移
5. 控制团队规模（3-5 个），模型分层（Haiku/Sonnet/Opus），及时关闭空闲队友

**范式转变**：从"提示词工程"到"AI 团队 orchestration"。你不再需要关注每一行代码怎么写，只需要定义清晰的业务目标、搭建合理的团队角色与分工、制定明确的验收标准。

> **实战建议**：从 2-3 个 Agent 的小团队开始，熟悉协作模式后再扩大到 5 个 Agent。记住，Agent Teams 是工具，核心决策权仍在你手中。
