# 11.6 实战：用Claude团队构建C编译器

> **案例背景**：2026年2月，Anthropic研究员Nicholas Carlini做了一个实验：用16个并行的Claude实例，从零开始写一个Rust实现的C编译器，要求能编译Linux内核。这个案例展现了Claude Code多智能体协作的极限能力，也揭示了上下文工程和长期自主工作的关键技巧。

## 架构设计：让Claude团队协同工作

### 核心挑战

传统的Claude Code会话需要人类在环（human-in-the-loop）：模型工作一段时间后会停下来等待指令。要让Claude**完全自主**工作，需要解决：

1. **持续工作**：如何让Claude在没有人类干预的情况下持续工作？
2. **并行协作**：多个Claude实例如何协同而不互相干扰？
3. **质量保证**：没有人类实时审查，如何确保代码质量？

### 解决方案：三层架构

```
┌──────────────────────────────────────────────────────────┐
│                  Harness（调度层）                          │
│          while true; do claude --dangerously-skip-permissions; done   │
└──────────────────────────────────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────┐
│              Parallel Agents（执行层）                      │
│  16个Docker容器，每个运行独立的Claude Code实例              │
│  共享Git仓库，通过文件锁同步任务                            │
└──────────────────────────────────────────────────────────┘
                           ↓
┌──────────────────────────────────────────────────────────┐
│              Test Harness（验证层）                         │
│  高质量的测试套件 + 持续集成流水线                          │
│  Claude自主运行测试、查看结果、修复问题                     │
└──────────────────────────────────────────────────────────┘
```

## 第一层：Harness（让Claude持续工作）

### 核心代码

```bash
#!/bin/bash
# harness.sh - 让Claude在容器中持续工作

while true; do
  COMMIT=$(git rev-parse --short=6 HEAD)
  LOGFILE="agent_logs/agent_${COMMIT}.log"
  
  claude --dangerously-skip-permissions \
    -p "$(cat AGENT_PROMPT.md)" \
    --model claude-opus-4.6 &> "$LOGFILE"
done
```

### Agent Prompt设计

```markdown
# AGENT_PROMPT.md

You are working on building a C compiler in Rust.

## Your workflow:
1. Read TODO.md to see current tasks
2. Pick an uncompleted task (create lock file to claim it)
3. Implement the feature, writing tests
4. Run tests to verify
5. Commit your changes with clear message
6. Push to upstream repo
7. Repeat from step 1

## Important:
- Always run tests before committing
- Write clear commit messages
- If stuck, document what you tried in NOTES.md
- Keep working until the compiler can compile Linux kernel
```

**关键设计**：
- `--dangerously-skip-permissions`：让Claude无需人类批准即可执行操作（仅在隔离容器中！）
- 无限循环：`while true`让Claude持续工作，除非遇到致命错误
- 日志文件：每个commit记录一个日志，方便后续分析

## 第二层：Parallel Agents（并行协作）

### 并行化策略

**问题**：16个Claude同时工作，如何避免冲突？

**解决方案**：基于文件的任务锁机制

```bash
# Claude的工作流程（伪代码）
1. 读取 TODO.md，选择任务 "implement_parse_if_statement"
2. 创建锁文件：touch current_tasks/parse_if_statement.txt
3. 实现功能，运行测试
4. git pull（拉取其他agent的更新）
5. git commit && git push
6. 删除锁文件：rm current_tasks/parse_if_statement.txt
7. 回到步骤1

# 其他Claude看到锁文件存在，会选择其他任务
```

### 冲突处理

**现实**：多个Claude同时`git push`会产生冲突。

**Claude的应对**：
- Claude能够自主解决git merge冲突
- 测试套件保证：合并后必须所有测试通过才能push成功
- 失败的push会触发自动修复流程

### 容器化隔离

```bash
# 每个Agent运行在独立的Docker容器中
for i in {1..16}; do
  docker run -d \
    --name "claude_agent_$i" \
    -v $(pwd)/upstream:/upstream \
    claude-compiler-env \
    bash harness.sh
done

# 共享仓库通过 volume mount 实现
# 每个容器内部：git clone /upstream /workspace
```

## 第三层：Test Harness（质量保证）

### 核心原则：测试套件是Claude的"眼睛"

> **关键洞察**：Claude的性能上限取决于测试套件的质量。如果测试写错了，Claude会优化错误的目标。

### 测试金字塔

```
                    ┌─────────────────┐
                    │   Linux 内核编译  │  ← 端到端测试（最慢，最少）
                    └─────────────────┘
              ┌───────────────────────┈┈
              │  开源项目编译（SQLite, Redis, ...）
              └───────────────────────┈┈
        ┌──────────────────────────────┈┈
        │  GCC torture 测试套件（99%通过率）
        └──────────────────────────────┈┈
  ┌─────────────────────────────────────┈┈
  │  单元测试（每个parser/codegen模块）
  └─────────────────────────────────────┈┈
```

### 实战技巧：分层测试策略

#### 1. 单元测试（最快反馈）

```rust
// tests/parser_test.rs
#[test]
fn test_parse_if_statement() {
    let code = "if (x > 0) { return 1; }";
    let result = parse(code).unwrap();
    assert_eq!(result, expected_ast);
}
```

Claude每次修改parser后，立即运行：`cargo test parser`

#### 2. 集成测试（中等反馈）

```bash
# tests/compile_test.sh
#!/bin/bash
for test in tests/c_tests/*.c; do
  ./compiler $test -o /tmp/output
  gcc $test -o /tmp/expected
  diff <(/tmp/output) <(/tmp/expected)
done
```

#### 3. 端到端测试（最慢，但最可靠）

```bash
# 编译Linux内核
make CC=./target/release/claude_cc -j16
qemu-system-x86_64 -kernel bzImage -nographic
# 如果启动成功，说明编译器工作正常
```

### 避免上下文污染

**问题**：测试输出太多，Claude的上下文窗口会被无用信息填满。

**解决方案**：

```bash
# 错误时只打印关键信息
if [ $? -ne 0 ]; then
  echo "ERROR: test_parse_if_statement failed at line 42"
  echo "Expected: ..." >> log.txt
  echo "Got: ..." >> log.txt
else
  echo "PASS: test_parse_if_statement"
fi

# Claude用grep查找错误
JournalAgent $ grep "ERROR" test_output.log
```

## 上下文工程：让Claude"站在自己肩膀上"

### 挑战：Claude没有"长期记忆"

每个Claude实例的上下文窗口有限（即使200K tokens也会填满）。当会话持续数小时，早期的决策会被"遗忘"。

### 解决方案：文件系统作为"外部记忆"

#### 1. TODO.md（任务追踪）

```markdown
# TODO.md

## In Progress
- [ ] Implement switch statement parsing (claimed by agent_3)
- [ ] Fix codegen for nested loops (claimed by agent_7)

## Pending  
- [ ] Add support for bitfields
- [ ] Optimize register allocation
- [ ] Implement inline assembly

## Completed
- [x] Basic expression parsing
- [x] If statement codegen
- [x] Function call convention (x86_64)
```

Claude每次开始工作前读取TODO.md，选择新任务。

#### 2. NOTES.md（决策日志）

```markdown
# NOTES.md

## 2026-02-10
Tried to implement switch statement with jump table, but 
performance was worse than if-else chain. Reverted to if-else.

## 2026-02-12
Found bug in register allocator: when function has >6 arguments,
we run out of caller-saved registers. Fix: spill to stack.

## Lesson Learned
Always run `cargo test` before committing. Forgot once, 
broke CI, wasted 2 hours debugging.
```

**价值**：新启动的Claude实例读取NOTES.md，立即获得项目历史背景。

#### 3. PROGRESS.md（进度追踪）

```markdown
# PROGRESS.md

## Compiler Components
- [x] Lexer (100%)
- [x] Parser (95%, switch statement WIP)  
- [ ] Semantic Analysis (80%)
- [ ] IR Generation (70%)
- [ ] Optimization Passes (30%)
- [ ] Code Generation (x86_64: 90%, ARM: 60%, RISC-V: 40%)

## Test Pass Rate
- Unit tests: 312/312 (100%)
- GCC torture: 1582/1600 (99%)
- Linux kernel compile: SUCCESS (x86_64, ARM, RISC-V)
```

## 并行化的艺术：让16个Claude高效协作

### 挑战：如何拆分任务？

**错误做法**：让16个Claude同时修改同一个文件（比如parser.rs），会产生大量冲突。

**正确做法**：任务粒度要足够小，且相互独立。

### 任务拆分策略

| 任务类型 | 示例 | 并行度 | 说明 |
|---------|------|--------|------|
| **独立功能** | 实现`switch`语句解析 | 高（16路） | 每个Claude做不同的语言特性 |
| **优化Pass** | 死代码消除、常量折叠 | 中（8路） | 每个优化Pass独立 |
| **后端架构** | x86_64 vs ARM vs RISC-V | 高（3路） | 不同架构的codegen独立 |
| **测试/文档** | 写测试、更新文档 | 高（16路） | 可与功能开发并行 |

### 实战：编译Linux内核的并行策略

**问题**：Linux内核是一个"大任务"，16个Claude都去编译kernel，会反复修复同一个bug。

**解决方案**：二分查找 + 随机采样

```python
# test_harness/bisect_linux.py
import random

def compile_linux_with_bisect(compiler, start_file, end_file):
    """用二分法找到导致编译失败的文件"""
    mid = (start_file + end_file) // 2
    
    # 前半部分用Claude的编译器，后半部分用GCC
    compile_with_mixed(compiler, 0, mid, "claude")
    compile_with_mixed(compiler, mid+1, end_file, "gcc")
    
    if kernel_boots():
        # 问题在后半部分
        return compile_linux_with_bisect(compiler, mid+1, end_file)
    else:
        # 问题在前半部分
        return compile_linux_with_bisect(compiler, start_file, mid)
```

**随机采样加速**：

```bash
# 每个Agent编译1%的随机文件，快速定位问题
for agent in {1..16}; do
  ./test_harness/random_sample.sh 1% &
done
wait
# 汇总失败的文件，针对性修复
```

## 专业角色分工（Multi-Role Agents）

并行化不仅是"更多Claude做同一件事"，还可以**专业化分工**：

```markdown
# ROLES.md

## Agent Roles

### FrontendAgent (2个实例)
- 负责：Lexer, Parser, Semantic Analysis
- 技能要求：熟悉C语言标准，AST设计

### OptimizationAgent (2个实例)  
- 负责：IR优化Pass（死代码消除、循环优化等）
- 技能要求：编译器优化理论

### CodegenAgent (3个实例)
- 负责：x86_64, ARM, RISC-V 代码生成
- 技能要求：熟悉汇编，调用约定

### TestAgent (1个实例)
- 负责：维护测试套件，运行CI
- 技能要求：GCC torture测试，QEMU使用

### DocAgent (1个实例)
- 负责：更新README, NOTES, 写注释
- 技能要求：技术写作

### PerformanceAgent (1个实例)
- 负责：编译器性能分析，生成的代码质量
- 技能要求：perf, 汇编优化

### 主Agent (6个实例)
- 负责：通用任务，填补上述角色的空白
```

**效果**：专业化分工让每个Agent深度优化自己的领域，而不是"浅尝辄止"。

## 经验教训：什么有效，什么无效

### ✅ 有效策略

#### 1. 测试套件是"上帝"

> **教训**：如果测试套件有bug，Claude会优化错误的目标。

**案例**：
- 初期测试套件允许`1+2=4`，Claude居然"学会"了错误答案
- 修复测试套件后，Claude立即修正

**建议**：
- 测试套件必须经过人类审查
- 使用业界标准测试（如GCC torture）
- 端到端测试不可少（编译Linux内核是最强的验证）

#### 2. 文件系统 > 上下文窗口

> **教训**：试图把所有信息都塞进Claude的上下文，会导致"上下文污染"。

**正确做法**：
- 用`TODO.md`, `NOTES.md`, `PROGRESS.md`作为"外部记忆"
- Claude需要时主动读取这些文件
- 日志输出要简洁，用`grep "ERROR"`过滤

#### 3. 让Claude"看见"进度

> **心理学的启示**：人类需要看见进度条才有动力，Claude也需要。

**做法**：
```bash
# 每次commit后自动更新PROGRESS.md
git hook: post-commit
  ./scripts/update_progress.sh
  cat PROGRESS.md  # Claude能"看到"整体进度
```

#### 4. 接受不完美，快速迭代

> **教训**：初期试图让Claude"一次做对"，结果效率极低。

**正确做法**：
- 允许Claude提交不完美的代码（只要有测试保护）
- CI自动捕获回归
- Claude从错误中学习（记录在NOTES.md）

### ❌ 无效策略

#### 1. 过度复杂的任务分配算法

> **教训**：试图用中心化调度器分配任务，反而降低效率。

**原因**：
- Claude自己会选择"下一个最明显的任务"
- 中心化调度需要频繁通信，成为瓶颈

**正确做法**：
- 用简单的文件锁（touch lock_file）
- 让Claude自主决策

#### 2. 人类频繁干预

> **教训**：每30分钟检查一次进度并"指导"，反而打断Claude的工作流。

**正确做法**：
- 设定清晰的目标和测试标准
- 让Claude自主工作数小时
- 只在CI失败或Claude卡住时介入

#### 3. 忽略上下文窗口限制

> **教训**：让Claude一次性处理100个文件，上下文窗口爆炸，性能急剧下降。

**正确做法**：
- 任务粒度要小（每个任务改1-3个文件）
- 用`/compact`定期压缩上下文
- 拆分会话：一个会话专注一个子任务

## 结果评估：Claude团队的能力边界

### 成功指标

| 指标 | 结果 |
|------|------|
| **代码规模** | 100,000+ 行Rust代码 |
| **测试通过率** | 99%（GCC torture） |
| **真实项目编译** | Linux 6.9, SQLite, Redis, QEMU, FFmpeg |
| **多架构支持** | x86_64, ARM, RISC-V |
| **成本** | $20,000（200亿输入token + 1.4亿输出token） |

### 局限性（Claude目前做不到的）

1. **16-bit x86编译器**：需要编译Linux实模式代码（<64KB），Claude生成的代码超过60KB。目前仍调用GCC处理这部分。

2. **独立的汇编器和链接器**：编译器仍依赖GCC的assembler和linker。

3. **生成代码效率**：即使开启所有优化，生成的代码仍比GCC -O0（无优化）慢。

4. **Rust代码质量**：能工作，但架构设计不如专家级Rust程序员。

### 与人工对比

| 维度 | 人工团队 | Claude团队 |
|------|---------|-----------|
| **时间** | 6-12个月 | 2周 |
| **成本** | $200,000+ | $20,000 |
| **代码质量** | 高 | 中等（能工作，但不够优雅） |
| **测试覆盖** | 依赖团队纪律 | 强制（测试驱动开发） |
| **文档** | 经常落后 | 自动生成（DocAgent维护） |

**结论**：Claude团队适合**快速原型**和**达到"能用"的标准**，但**还不能完全替代**顶级人工团队。

## 如何复现这个实验？

### 前置条件

1. **API Budget**：需要至少$20,000的Claude API额度（或等价的Claude Max订阅）
2. **Docker环境**：16核CPU + 32GB RAM（运行16个容器）
3. **测试套件**：提前准备好高质量的编译器测试（GCC torture, CSmith等）

### 快速启动

```bash
# 1. 克隆仓库
git clone https://github.com/anthropics/claudes-c-compiler
cd claudes-c-compiler

# 2. 启动Harness（单Agent测试）
bash harness.sh

# 3. 如果单Agent工作正常，扩展到16个并行Agent
for i in {1..16}; do
  docker run -d --name "agent_$i" \
    -v $(pwd):/workspace \
    claude-compiler-env \
    bash harness.sh
done

# 4. 监控进度
watch -n 60 "cat PROGRESS.md"
```

### 降低成本的方法

如果预算有限，可以：

1. **减少Agent数量**：从16个降到4个，成本降至$5,000
2. **使用Sonnet模型**：Opus 4.6成本高，Sonnet便宜5倍
3. **缩小目标**：不编译Linux内核，只编译SQLite + Redis
4. **复用现有编译器**：基于LLVM写前端，而不是从零实现

## 对你的启示：如何应用这些经验？

### 场景1：大型代码库重构

**传统做法**：人工逐个模块重构，耗时数周。

**Claude团队做法**：
1. 用16个Claude并行重构不同模块
2. 每个Claude负责一个package/namespace
3. 测试套件保证重构不引入bug
4. 预计节省时间：**80%**（2周 → 3天）

### 场景2：多平台适配

**传统做法**：人工为每个平台（Windows/macOS/Linux）适配代码。

**Claude团队做法**：
1. 启动3个Claude，分别负责一个平台
2. 共享测试套件，保证行为一致
3. 预计节省时间：**70%**（1周 → 2天）

### 场景3：文档和测试补全

**传统做法**：代码写完，文档和测试"永远明天再做"。

**Claude团队做法**：
1. 主Claude写代码
2. DocAgent自动生成文档
3. TestAgent自动生成单元测试
4. 预计节省时间：**50%**（减少技术债）

## 总结：多智能体协作的三条铁律

1. **测试套件是"上帝"**：没有高质量测试，Claude会优化错误的目标。
2. **文件系统作为外部记忆**：不要让上下文窗口成为瓶颈，用文件持久化关键信息。
3. **专业化分工 > 暴力并行**：16个通用Claude不如12个通用 + 4个专家。

**展望**：随着模型能力提升，未来Claude团队能完成的任务会越来越复杂。2026年能写编译器，2027年或许能设计操作系统。

**行动建议**：从今天开始，尝试用2-3个Claude并行处理你的下一个大项目。你会惊讶于效率的提升。
