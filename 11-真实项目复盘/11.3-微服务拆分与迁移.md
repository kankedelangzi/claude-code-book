## 一、背景：单体应用的痛点

### 1.1 典型单体架构的问题

```
┌─────────────────────────────────────────────────┐
│           单体电商系统 (Monolith)                │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐       │
│  │ 用户模块 │  │ 订单模块 │  │ 支付模块 │  ...  │
│  └─────────┘  └─────────┘  └─────────┘       │
│                    ↓                            │
│          共享数据库 (500+ 张表)                 │
└─────────────────────────────────────────────────┘
```

**痛点清单**：
- ✗ 代码耦合严重，改一个模块影响全局
- ✗ 数据库成为瓶颈，单表超过 5000 万行
- ✗ 部署成本高，改一行代码要重启整个应用
- ✗ 技术栈升级困难，想用 Spring Boot 3.0？得全系统一起改
- ✗ 团队协作用户、订单、支付的开发者互相"踩脚"

## 二、微服务拆分方法论

### 2.1 领域驱动设计（DDD）核心概念

微服务的拆分 **不能拍脑袋**，需要方法论指导。领域驱动设计（Domain-Driven Design，DDD）是业界公认的最佳实践。

#### 核心概念速查表

| 概念 | 定义 | 微服务映射 |
|------|------|-----------|
| **限界上下文（Bounded Context）** | 业务能力的语义边界 | 微服务边界 |
| **聚合根（Aggregate Root）** | 聚合的根实体，外部只能通过它访问聚合 | 微服务内的核心实体 |
| **领域事件（Domain Event）** | 领域中发生的重要业务事件 | 微服务间异步通信 |
| **核心域（Core Domain）** | 业务差异化的关键领域 | 高优先级投入的微服务 |
| **支撑域（Supporting Domain）** | 支撑核心业务的领域 | 辅助微服务 |
| **通用域（Generic Domain）** | 通用业务逻辑 | 可购买或开源的微服务 |

#### DDD 拆分流程

```
业务全景梳理
    ↓
事件风暴（Event Storming）工作坊
    ↓
识别领域对象、命令、事件
    ↓
划分限界上下文（Bounded Context）
    ↓
定义聚合根和值对象
    ↓
确定微服务边界
    ↓
设计数据库拆分方案
```

### 2.2 拆分策略选择

#### 策略一：绞杀者模式（Strangler Fig Pattern）⭐ 推荐

**核心思想**：在单体应用外围逐步构建新功能，最终"绞杀"掉单体应用。

```
阶段 1: API Gateway 分流
┌────────────┐
│   用户     │
└─────┬──────┘
      │
┌─────▼──────────────────────────┐
│       API Gateway              │
│  /api/v1/* → 单体应用         │
│  /api/v2/* → 新微服务 (逐步)  │
└────────────────────────────────┘

阶段 2: 抽离高价值模块
┌────────────┐
│   用户     │
└─────┬──────┘
      │
┌─────▼──────────────────────────┐
│       API Gateway              │
│  /users/*    → 用户微服务     │
│  /orders/*   → 订单微服务     │
│  /products/* → 产品微服务     │
│  其他         → 单体应用       │
└────────────────────────────────┘

阶段 3: 数据库解耦
- 每个微服务拥有独立数据库
- 通过 CDC（Change Data Capture）实现数据同步

阶段 4: 事件驱动异步化
- 引入消息队列（Kafka/RabbitMQ）
- 微服务间通过领域事件通信

阶段 5: 完成迁移
- 单体应用功能全部迁移完毕
- 关闭单体应用
```

#### 策略二：数据库先行拆分

**适用场景**：数据库已成为主要瓶颈，需要优先解决。

**步骤**：
1. **垂直拆分**：按业务将表拆分到不同数据库
   - 用户库：users, user_profiles, addresses
   - 订单库：orders, order_items, cart
   - 商品库：products, categories, inventory

2. **水平拆分**：单表数据量过大时，按分片键拆分
   - 订单表按 `user_id` 分片
   - 商品表按 `category_id` 分片

3. **应用层适配**：通过 Service 层统一访问数据源

package com.ecommerce.user.controller;

import com.ecommerce.user.dto.UserRegistrationDto;
import com.ecommerce.user.entity.User;
import com.ecommerce.user.service.UserService;
import jakarta.validation.Valid;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import java.util.Optional;

@RestController
@RequestMapping("/api/v1/users")
public class UserController {
    
    @Autowired
    private UserService userService;
    
    @PostMapping("/register")
    public ResponseEntity<User> registerUser(@Valid @RequestBody UserRegistrationDto dto) {
        User registeredUser = userService.registerUser(dto);
        return new ResponseEntity<>(registeredUser, HttpStatus.CREATED);
    }
    
    @GetMapping("/{username}")
    public ResponseEntity<User> getUserByUsername(@PathVariable String username) {
        Optional<User> userOpt = userService.findByUsername(username);
        return userOpt.map(ResponseEntity::ok)
                     .orElse(ResponseEntity.notFound().build());
    }
    
    @PutMapping("/{userId}/profile")
    public ResponseEntity<User> updateProfile(
            @PathVariable Long userId,
            @Valid @RequestBody UserProfile profile) {
        User updatedUser = userService.updateUserProfile(userId, profile);
        return ResponseEntity.ok(updatedUser);
    }
}

-- user_db（用户数据库）
CREATE TABLE users (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    username VARCHAR(50) UNIQUE NOT NULL,
    email VARCHAR(100) UNIQUE,
    phone_number VARCHAR(20) UNIQUE,
    password VARCHAR(255) NOT NULL,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,

    INDEX idx_username (username),
    INDEX idx_email (email)

CREATE TABLE user_profiles (
    user_id BIGINT PRIMARY KEY,
    real_name VARCHAR(100),
    avatar_url VARCHAR(255),
    bio TEXT,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

CREATE TABLE addresses (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL,
    province VARCHAR(50),
    city VARCHAR(50),
    district VARCHAR(50),
    detail VARCHAR(255),
    is_default BOOLEAN DEFAULT FALSE,
    FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE,
    INDEX idx_user_id (user_id)
);

-- order_db（订单数据库）
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_no VARCHAR(32) UNIQUE NOT NULL,
    user_id BIGINT NOT NULL,  -- 注意：只存 user_id，不存用户信息
    total_amount DECIMAL(10, 2) NOT NULL,
    status ENUM('PENDING', 'PAID', 'SHIPPED', 'COMPLETED', 'CANCELLED') DEFAULT 'PENDING',
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_user_id (user_id),
    INDEX idx_order_no (order_no),
    INDEX idx_status (status)
);

CREATE TABLE order_items (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_id BIGINT NOT NULL,
    product_id BIGINT NOT NULL,  -- 只存 product_id，不存商品详情
    quantity INT NOT NULL,
    price DECIMAL(10, 2) NOT NULL,
    FOREIGN KEY (order_id) REFERENCES orders(id) ON DELETE CASCADE,
    INDEX idx_order_id (order_id)
);

**Step 2: 使用阿里巴巴 Canal 进行 CDC**

```java
// Canal 配置（canal.properties）
canal.instance.filter.regex=.*\\..*
canal.instance.filter.black.regex=mysql\\.slave_.*

// Spring Boot 集成 Canal
@Component
public class UserDataSyncListener {
    
    @Autowired
    private UserSyncService userSyncService;
    
    @CanalListener(destination = "example")
    public void onMessage(CanalEntry.Entry entry) {
        if (entry.getEntryType() == CanalEntry.EntryType.ROWDATA) {
            CanalEntry.RowChange rowChange = CanalEntry.RowChange.parseFrom(entry.getStoreValue());
            
            for (CanalEntry.RowData rowData : rowChange.getRowDatasList()) {
                switch (rowChange.getEventType()) {
                    case INSERT:
                        handleInsert(rowData);
                        break;
                    case UPDATE:
                        handleUpdate(rowData);
                        break;
                    case DELETE:
                        handleDelete(rowData);
                        break;
                }
            }
        }
    }
    
    private void handleInsert(CanalEntry.RowData rowData) {
        User user = parseUserFromRowData(rowData.getAfterColumnsList());
        userSyncService.syncToNewDb(user);
    }
    
    private void handleUpdate(CanalEntry.RowData rowData) {
        User user = parseUserFromRowData(rowData.getAfterColumnsList());
        userSyncService.updateInNewDb(user);
    }
    
    private void handleDelete(CanalEntry.RowData rowData) {
        Long userId = getUserIdFromRowData(rowData.getBeforeColumnsList());
        userSyncService.deleteFromNewDb(userId);
    }
}
```

public class UserServiceImpl implements UserService {

    private UserRepository oldUserRepository;  // 旧库
    
    @Autowired
    private NewUserRepository newUserRepository; // 新库
    
    @Transactional

    public User registerUser(UserRegistrationDto dto) {
        // 1. 写入旧库（保证原有系统正常运行）

        // 2. 写入新库（微服务的新数据库）

    }
}

### 4.2 异步通信（领域事件 + Kafka）

**场景**：用户注册后，发送欢迎邮件、初始化积分账户

// user-service 发布领域事件
@Service
public class UserServiceImpl implements UserService {
    
    @Autowired
    private KafkaTemplate<String, Object> kafkaTemplate;
    
    @Override
    public User registerUser(UserRegistrationDto dto) {
        // 1. 保存用户
        User user = new User();
        // ... 赋值
        userRepository.save(user);
        
        // 2. 发布领域事件（异步）
        UserRegisteredEvent event = new UserRegisteredEvent();
        event.setUserId(user.getId());
        event.setUsername(user.getUsername());
        event.setEmail(user.getEmail());
        event.setOccurredAt(Instant.now());
        
        kafkaTemplate.send("user-events", event);
        
        return user;
    }
}

## 六、常见问题与解决方案

### Q1: 微服务拆分后，跨服务查询怎么办？

**问题**：原来一个 SQL 的 JOIN 查询，现在需要调用多个服务。

**解决方案**：
1. **API 组合（API Composition）**：在 API 网关层或专用聚合服务中调用多个服务，组装数据
2. **CQRS 模式**：使用专门的读模型（Read Model）存储冗余数据，避免实时调用
3. **事件溯源（Event Sourcing）**：通过重放事件构建投影（Projection）

**示例：API 组合**
```java
@RestController
public class OrderAggregateController {
    
    @Autowired
    private OrderService orderService;
    
    @Autowired
    private UserServiceClient userServiceClient;
    
    @Autowired
    private ProductServiceClient productServiceClient;
    
    @GetMapping("/orders/{orderId}/details")
    public OrderDetailsDto getOrderDetails(@PathVariable Long orderId) {
        // 1. 获取订单
        Order order = orderService.getOrder(orderId);
        
        // 2. 获取用户信息
        UserDto user = userServiceClient.getUser(order.getUserId());
        
        // 3. 获取商品信息
        List<OrderItemDto> items = order.getItems().stream()
            .map(item -> {
                ProductDto product = productServiceClient.getProduct(item.getProductId());
                return convertToDto(item, product);
            })
            .collect(Collectors.toList());
        
        // 4. 组装结果
        return OrderDetailsDto.builder()
            .order(order)
            .user(user)
            .items(items)
            .build();
    }
}
```

### Q2: 分布式事务如何处理？

**问题**：订单服务扣款后，调用支付服务失败，如何回滚？

**解决方案**：
1. **Saga 模式**：通过一系列本地事务 + 补偿事务实现最终一致性
2. **TCC 模式**（Try-Confirm-Cancel）：预留资源 → 确认/取消
3. **事务消息**：基于消息队列实现最终一致性

**示例：Saga 模式**
```java
// 订单服务 - Saga 协调器
@Service
public class OrderSagaService {
    
    @Autowired
    private KafkaTemplate<String, Object> kafkaTemplate;
    
    @Transactional
    public void createOrderSaga(OrderDto orderDto) {
        // Step 1: 创建订单（状态：PENDING）
        Order order = createPendingOrder(orderDto);
        
        // Step 2: 发送 Saga 启动事件
        OrderCreatedEvent event = new OrderCreatedEvent();
        event.setOrderId(order.getId());
        event.setUserId(orderDto.getUserId());
        event.setTotalAmount(orderDto.getTotalAmount());
        event.setItems(orderDto.getItems());
        
        kafkaTemplate.send("order-saga", event);
    }
}

// 支付服务 - Saga 参与者
@Service
public class PaymentSagaListener {
    
    @KafkaListener(topics = "order-saga", groupId = "payment-group")
    @Transactional
    public void handleOrderCreated(OrderCreatedEvent event) {
        try {
            // 执行支付
            Payment payment = processPayment(event);
            
            // 发送支付成功事件
            PaymentCompletedEvent completedEvent = new PaymentCompletedEvent();
            completedEvent.setOrderId(event.getOrderId());
            completedEvent.setPaymentId(payment.getId());
            
            kafkaTemplate.send("order-saga-completed", completedEvent);
            
        } catch (Exception e) {
            // 发送支付失败事件（触发补偿事务）
            PaymentFailedEvent failedEvent = new PaymentFailedEvent();
            failedEvent.setOrderId(event.getOrderId());
            failedEvent.setReason(e.getMessage());
            
            kafkaTemplate.send("order-saga-failed", failedEvent);
        }
    }
}
```

### Q3: 数据库拆分后，跨库 JOIN 怎么办？

**解决方案**：
1. **冗余字段**：将常用查询字段冗余到主表中
2. **API 组合**：在应用层调用多个服务，组装数据
3. **数据同步**：使用 CDC 将其他服务的数据同步到本地读库

**示例：冗余字段**
```sql
-- 订单表冗余商品名称（避免实时调用商品服务）
CREATE TABLE orders (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    order_no VARCHAR(32),
    user_id BIGINT,
    total_amount DECIMAL(10, 2),
    -- 冗余字段（从商品服务同步）
    product_name VARCHAR(200),
    product_image VARCHAR(255),
    INDEX idx_order_no (order_no)
);
```

### 7.1 微服务拆分检查清单

- [ ] 使用 DDD 进行领域建模，识别限界上下文
- [ ] 定义清晰的微服务接口（REST / gRPC）
- [ ] 每个微服务拥有独立数据库
- [ ] 使用 API 网关统一入口
- [ ] 引入服务注册与发现（Eureka / Nacos）
- [ ] 配置中心管理（Spring Cloud Config / Nacos）
- [ ] 熔断降级机制（Resilience4j / Sentinel）
- [ ] 分布式追踪（Sleuth + Zipkin）
- [ ] 日志聚合（ELK Stack）
- [ ] 持续集成 / 持续部署（Jenkins / GitLab CI）

### 7.2 拆分优先级建议

| 优先级 | 服务 | 理由 |
|--------|------|------|
| P0 | 用户服务 | 基础服务，耦合度低 |
| P0 | 订单服务 | 核心业务，独立性强 |
| P1 | 商品服务 | 读多写少，适合缓存优化 |
| P1 | 支付服务 | 对安全性要求高，独立部署 |
| P2 | 通知服务 | 异步处理，解耦核心业务 |
| P3 | 推荐服务 | AI/ML 密集型，独立扩展 |
