# 8.2 Docker 容器化实战

> 从 Dockerfile 到 docker-compose，一条龙搞定。

## 🎯 场景描述

容器化是部署的标准方式，但写好 Dockerfile 也是门学问：

- 镜像体积太大，推送慢、拉取慢
- 多阶段构建搞不明白
- docker-compose 的网络和服务依赖理不清
- 开发环境和生产环境的配置切换麻烦

**Claude Code 可以帮你写出优化的 Dockerfile 和 Compose 配置。**

## ✨ 案例一：优化 Node.js 项目的 Dockerfile

### 传统做法

随便搜一个 Dockerfile 模板，复制粘贴：

```dockerfile
# 新手常犯的错误版本
FROM node:20
WORKDIR /app
COPY . .
RUN npm install
EXPOSE 3000
CMD ["npm", "start"]
# 问题：镜像 1.2GB，每次都重新安装依赖，node_modules 也被打包进去了
```

### Claude Code 做法

```
帮我优化这个 Node.js 项目的 Dockerfile（Next.js + pnpm）：
1. 多阶段构建，最终镜像用 alpine
2. 利用 Docker 缓存层，依赖不变时跳过安装
3. 只复制必要的文件
4. 用非 root 用户运行
5. 目标镜像体积 < 200MB
```

生成的优化版本：

```dockerfile
# Dockerfile
# ---- 阶段1：安装依赖 ----
FROM node:20-alpine AS deps
RUN corepack enable && corepack prepare pnpm@8 --activate
WORKDIR /app

COPY package.json pnpm-lock.yaml ./
RUN pnpm install --frozen-lockfile --prod=false

# ---- 阶段2：构建 ----
FROM node:20-alpine AS builder
RUN corepack enable && corepack prepare pnpm@8 --activate
WORKDIR /app

COPY --from=deps /app/node_modules ./node_modules
COPY . .

ENV NEXT_TELEMETRY_DISABLED=1
RUN pnpm build

# ---- 阶段3：生产运行 ----
FROM node:20-alpine AS runner
WORKDIR /app

ENV NODE_ENV=production
ENV NEXT_TELEMETRY_DISABLED=1

RUN addgroup --system --gid 1001 nodejs && \
    adduser --system --uid 1001 nextjs

# 只复制构建产物
COPY --from=builder /app/public ./public
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static

USER nextjs
EXPOSE 3000

ENV PORT=3000
ENV HOSTNAME="0.0.0.0"

CMD ["node", "server.js"]
```

### 镜像体积对比

| 版本 | 体积 | 构建时间 |
|------|------|---------|
| 新手版 | ~1.2 GB | 慢（每次重装依赖）|
| 优化版 | ~180 MB | 快（利用缓存层）|

## ✨ 案例二：多服务 docker-compose

### 需求

```
帮我写一个 docker-compose.yml，包含以下服务：
1. Next.js 前端（端口 3000）
2. Express API 后端（端口 4000）
3. PostgreSQL 数据库
4. Redis 缓存
5. Nginx 反向代理（端口 80）
6. 健康检查
7. 开发环境热更新支持
```

### Claude Code 生成

```yaml
# docker-compose.yml
version: "3.8"

services:
  # ---- 前端 ----
  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile.dev
    ports:
      - "3000:3000"
    volumes:
      - ./frontend/src:/app/src
      - ./frontend/public:/app/public
    environment:
      - NEXT_PUBLIC_API_URL=http://localhost:4000
    depends_on:
      backend:
        condition: service_healthy

  # ---- 后端 ----
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile.dev
    ports:
      - "4000:4000"
    volumes:
      - ./backend/src:/app/src
    environment:
      - DATABASE_URL=postgresql://app:secret@db:5432/myapp
      - REDIS_URL=redis://cache:6379
      - JWT_SECRET=${JWT_SECRET}
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:4000/health"]
      interval: 10s
      timeout: 5s
      retries: 3

  # ---- 数据库 ----
  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
      POSTGRES_DB: myapp
    ports:
      - "5432:5432"
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      timeout: 3s
      retries: 5

  # ---- 缓存 ----
  cache:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    volumes:
      - redisdata:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 5

  # ---- 反向代理 ----
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
    depends_on:
      - frontend
      - backend

volumes:
  pgdata:
  redisdata:
```

### 配套的 Nginx 配置

```
再帮我写一个 nginx.conf：
/api 路径转发到后端 4000 端口，
其他路径转发到前端 3000 端口，
开启 gzip 压缩
```

```nginx
# nginx/nginx.conf
events {
    worker_connections 1024;
}

http {
    gzip on;
    gzip_types text/plain text/css application/json application/javascript text/xml;
    gzip_min_length 1000;

    upstream backend {
        server backend:4000;
    }

    upstream frontend {
        server frontend:3000;
    }

    server {
        listen 80;

        location /api/ {
            proxy_pass http://backend;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
        }

        location / {
            proxy_pass http://frontend;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header Upgrade $http_upgrade;
            proxy_set_header Connection "upgrade";
        }
    }
}
```

## ✨ 案例三：Dockerfile 安全加固

### Claude Code 做法

```
审查并加固这个 Dockerfile 的安全性，
要求：
1. 固定基础镜像版本（不用 latest）
2. 非 root 运行
3. 不存储密钥
4. 最小化安装包
5. 设置只读文件系统
```

Claude Code 的加固输出：

```dockerfile
# 安全加固要点（Claude Code 会指出的问题）

# ❌ 不要这样做
FROM node:latest              # 未固定版本，随时可能变
COPY .env .                   # 密钥进镜像了
RUN apt-get update            # 没有清理缓存

# ✅ 应该这样做
FROM node:20.11.0-alpine      # 固定版本
# .env 通过环境变量注入，不写进镜像
RUN apk add --no-cache xxx && \
    rm -rf /var/cache/apk/*  # 安装完清理缓存
USER nonroot                  # 非 root 运行
```

## 🔧 进阶技巧

### 1. 让 Claude Code 分析现有镜像

```
分析一下这个镜像的层级，帮我找出可以优化的地方
```

然后粘贴 `docker history` 的输出，它会帮你找出哪层最大、哪些可以合并。

### 2. 生成 .dockerignore

```
帮我生成 .dockerignore 文件，排除所有不必要的文件：
node_modules、.git、*.md、test、.env*
```

### 3. 区分开发和生产的 Compose

```
帮我拆分 docker-compose，把开发依赖和生产环境分开：
- docker-compose.yml：共享配置
- docker-compose.override.yml：开发环境额外配置（热更新、调试端口）
- docker-compose.prod.yml：生产环境配置
```

---

## ⚠️ 注意事项

1. **密钥永远不写进镜像** — 用环境变量或 Docker Secrets
2. **不要用 latest 标签** — 固定版本号，避免"昨天还能跑今天就挂了"
3. **生产环境用多阶段构建** — 减小攻击面和镜像体积
4. **健康检查一定要加** — Docker 和编排系统靠它判断服务状态

## 🎓 学到了什么

1. **多阶段构建是 Dockerfile 优化的核心** — Claude Code 最擅长帮你拆分阶段
2. **docker-compose 的 depends_on + healthcheck 是服务编排的保障** — 别让前端等后端，后端等数据库
3. **安全加固不是锦上添花，是必须操作** — 让 Claude Code 帮你做一轮安全审查
4. **镜像优化能省下大量时间和带宽** — 从 1GB 降到 200MB 不是夸张
