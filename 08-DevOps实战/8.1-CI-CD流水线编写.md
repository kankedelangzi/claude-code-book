# 8.1 CI/CD 流水线编写

> 别手写 YAML 了，让 Claude Code 帮你搞定流水线配置。

## 🎯 场景描述

CI/CD 是现代开发的标配，但配置文件往往是最让人头疼的部分：

- GitHub Actions 的 YAML 语法记不住
- Jenkinsfile 的 Groovy 语法更难搞
- GitLab CI 的 stages 和 rules 绕来绕去
- 环境变量、密钥管理、缓存配置一堆坑

**Claude Code 能根据你的项目结构，自动生成适合的 CI/CD 配置。**

## ✨ 案例一：GitHub Actions — Node.js 项目自动部署

### 传统做法

手动查文档，拼凑 YAML，反复调试：

```yaml
# 经常写错的地方：
# - node-version 写成了 node_version
# - 缓存路径不对，每次都重新安装依赖
# - 密钥配置漏了权限
# - 触发条件写错，push 了不跑
```

### Claude Code 做法

```
帮我为这个 Next.js 项目创建 GitHub Actions 配置：
1. PR 时自动跑 lint + test + build
2. 推送到 main 时自动部署到 Vercel
3. Node.js 20，用 pnpm
4. 缓存 node_modules
5. 超时时间 10 分钟
```

它直接生成：

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
    branches: [main, develop]
  push:
    branches: [main]

concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 10
    
    steps:
      - uses: actions/checkout@v4

      - uses: pnpm/action-setup@v2
        with:
          version: 8

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: pnpm

      - run: pnpm install --frozen-lockfile

      - run: pnpm lint
      - run: pnpm test --coverage
      - run: pnpm build

  deploy:
    needs: check
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    runs-on: ubuntu-latest
    timeout-minutes: 10
    
    steps:
      - uses: actions/checkout@v4
      - uses: amondnet/vercel-action@v25
        with:
          vercel-token: ${{ secrets.VERCEL_TOKEN }}
          vercel-org-id: ${{ secrets.VERCEL_ORG_ID }}
          vercel-project-id: ${{ secrets.VERCEL_PROJECT_ID }}
          vercel-args: --prod
```

| 步骤 | 手写 | Claude Code |
|------|------|-------------|
| 查文档找语法 | 15 分钟 | 0 分钟 |
| 写配置 | 20 分钟 | 30 秒（描述需求）|
| 调试缓存/权限 | 10 分钟 | 0 分钟 |

## ✨ 案例二：GitLab CI — 多环境部署

### 需求

```
项目是 Spring Boot + Gradle，需要 GitLab CI 配置：
1. dev 分支推送到开发环境（自动）
2. main 分支推送到预发环境（自动）
3. 打 tag 时推送到生产环境（自动）
4. 每个环境都要跑测试、构建镜像、部署
5. 用 Docker，镜像推到阿里云 ACR
```

### Claude Code 生成的配置

```yaml
# .gitlab-ci.yml
variables:
  REGISTRY: registry.cn-shanghai.aliyuncs.com
  IMAGE_NAME: mygroup/myapp
  DOCKER_TLS_CERTDIR: "/certs"

stages:
  - test
  - build
  - deploy

test:
  stage: test
  image: eclipse-temurin:17-jdk
  script:
    - ./gradlew test
  artifacts:
    reports:
      junit: build/test-results/test/*.xml
  rules:
    - if: $CI_PIPELINE_SOURCE == "merge_request_event"
    - if: $CI_COMMIT_BRANCH == "main"
    - if: $CI_COMMIT_BRANCH == "dev"

build:
  stage: build
  image: docker:24
  services:
    - docker:24-dind
  script:
    - docker login -u $ACR_USER -p $ACR_PASSWORD $REGISTRY
    - docker build -t $REGISTRY/$IMAGE_NAME:$CI_COMMIT_SHORT_SHA .
    - docker push $REGISTRY/$IMAGE_NAME:$CI_COMMIT_SHORT_SHA
    - |
      if [ "$CI_COMMIT_BRANCH" = "main" ]; then
        docker tag $REGISTRY/$IMAGE_NAME:$CI_COMMIT_SHORT_SHA $REGISTRY/$IMAGE_NAME:staging
        docker push $REGISTRY/$IMAGE_NAME:staging
      fi
  rules:
    - if: $CI_COMMIT_BRANCH == "dev"
    - if: $CI_COMMIT_BRANCH == "main"
    - if: $CI_COMMIT_TAG

deploy_dev:
  stage: deploy
  image: alpine
  script:
    - apk add --no-cache curl
    - |
      curl -X POST $DEV_WEBHOOK \
        -H "Content-Type: application/json" \
        -d '{"image":"registry.cn-shanghai.aliyuncs.com/mygroup/myapp:'$CI_COMMIT_SHORT_SHA'"}'
  environment:
    name: development
  rules:
    - if: $CI_COMMIT_BRANCH == "dev"

deploy_staging:
  stage: deploy
  image: alpine
  script:
    - apk add --no-cache curl
    - |
      curl -X POST $STAGING_WEBHOOK \
        -H "Content-Type: application/json" \
        -d '{"image":"registry.cn-shanghai.aliyuncs.com/mygroup/myapp:staging"}'
  environment:
    name: staging
  rules:
    - if: $CI_COMMIT_BRANCH == "main"

deploy_prod:
  stage: deploy
  image: alpine
  script:
    - apk add --no-cache curl
    - |
      curl -X POST $PROD_WEBHOOK \
        -H "Content-Type: application/json" \
        -d '{"image":"registry.cn-shanghai.aliyuncs.com/mygroup/myapp:'$CI_COMMIT_TAG'"}'
  environment:
    name: production
  rules:
    - if: $CI_COMMIT_TAG
```

### 关键技巧

告诉 Claude Code 你的实际环境信息：

```
我的 GitLab Runner 是自建的，用 Docker executor，
K8s 集群用的 rancher，部署通过 rancher API 触发
```

它生成的配置会更贴合你的架构。

## ✨ 案例三：修复失败的 CI 流水线

### 场景

CI 挂了，日志一大堆，不知道哪出了问题。

### Claude Code 做法

```
CI 跑失败了，这是日志：
[粘贴日志]

帮我分析失败原因并修复
```

它会：
1. 定位错误行
2. 分析根因（缺少依赖、权限不足、语法错误等）
3. 直接修改配置文件
4. 给出验证步骤

常见问题和 Claude Code 的修复方式：

| 错误 | 原因 | Claude Code 修复 |
|------|------|-----------------|
| `permission denied` | 缺少执行权限 | 加 `chmod +x` 或改脚本 |
| `cache not found` | 缓存 key 不匹配 | 改用 `hashFiles` |
| `timeout` | 超时太短 | 增加 timeout 或优化步骤 |
| `module not found` | 依赖没装 | 检查 lockfile 和 install 命令 |

## ✨ 案例四：Claude Code Security — 自动安全审查（2026-05 新功能）

> 🆕 **2026年5月27日发布** — Anthropic 推出 Claude Code 自动漏扫与修复插件，安全审查进入"零配置"时代。

### 问题场景

代码写完了，功能也测了，但你真的确定没有安全漏洞吗？

传统安全审查的痛点：
- SAST 工具配置复杂，误报率高得离谱
- 安全团队人手不够，审查排期以周计
- Vibe Coder 写的代码"表面光鲜如 PPT，内里全是坑"
- SQL 注入、XSS、硬编码密钥……防不胜防

### 两种使用方式

#### 方式一：终端里直接用 `/security-review`

最简单的方式——在 Claude Code 终端里直接输入：

```
/security-review
```

Claude 会立即开始检查你当前的代码变更，识别安全隐患：SQL 注入风险、XSS 漏洞、不安全的数据处理、硬编码密钥等。

发现漏洞后，直接让 Claude 修复就行：

```
/security-review
# Claude 发现 3 个问题：
# 1. [高危] SQL 注入：用户输入直接拼入查询字符串
# 2. [中危] XSS：未转义用户输入直接渲染到页面
# 3. [低危] 信息泄露：错误信息暴露了数据库结构

帮我修复这三个安全问题
```

#### 方式二：GitHub Actions 自动审查每个 PR

更强大的用法——每个 PR 自动触发安全审查，在代码合并前就把关。

创建 `.github/workflows/security.yml`：

```yaml
name: Security Review

permissions:
  pull-requests: write
  contents: read

on:
  pull_request:

jobs:
  security:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          ref: ${{ github.event.pull_request.head.sha || github.sha }}
          fetch-depth: 2

      - uses: anthropics/claude-code-security-review@main
        with:
          comment-pr: true
          claude-api-key: ${{ secrets.CLAUDE_API_KEY }}
```

配置完成后，每当有新 PR 提交，Claude 会自动：

1. **分析 diff** — 只看变更部分，精准高效
2. **上下文理解** — 理解代码的实际意图，不像传统 SAST 只做模式匹配
3. **生成发现** — 附带严重等级、详细解释和修复建议
4. **PR 内联评论** — 在具体代码行上添加审查意见
5. **误报过滤** — 自动过滤低影响或容易误报的问题

### 三阶段实时安全防护

2026年5月27日发布的自动漏扫插件更进一步，实现了**三阶段实时防护**：

| 阶段 | 触发时机 | 工作方式 | 是否消耗 API |
|------|----------|----------|-------------|
| **编辑时** | 你在写代码的过程中 | 本地规则实时匹配动态代码执行与高危模式 | ❌ 不消耗 |
| **会话结束时** | Claude Code 对话结束 | 后台模型比对工作区 git 差异，拦截逻辑漏洞 | ✅ 消耗 |
| **提交时** | `git commit` 或 `git push` | 深度智能体评审，读取调用链与消毒器上下文 | ✅ 消耗 |

**关键亮点**：编辑时的本地扫描不调用大模型，零额外 API 费用！

### 能检测哪些漏洞？

Claude Code Security 覆盖的漏洞类型非常全面：

| 类别 | 具体漏洞 |
|------|----------|
| **注入攻击** | SQL 注入、命令注入、LDAP 注入、XPath 注入、NoSQL 注入、XXE |
| **认证授权** | 破损认证、权限提升、不安全的直接对象引用、会话缺陷 |
| **数据泄露** | 硬编码密钥、敏感数据日志、信息泄露、PII 处理违规 |
| **加密问题** | 弱算法、不当密钥管理、不安全随机数生成 |
| **输入验证** | 缺少验证、不当消毒、缓冲区溢出 |
| **业务逻辑** | 竞态条件、TOCTOU 问题 |
| **配置安全** | 不安全默认值、缺少安全头、宽松 CORS |
| **供应链** | 脆弱依赖、拼写劫持风险 |
| **代码执行** | 反序列化 RCE、pickle 注入、eval 注入 |
| **XSS** | 反射型、存储型、DOM 型 |

同时自动过滤低影响或易误报的问题（DoS、速率限制、内存耗尽等），让你专注于真正重要的问题。

### 自定义安全规则

企业可以根据自己的安全需求定制审查规则：

```yaml
# .github/workflows/security.yml（自定义版）
- uses: anthropics/claude-code-security-review@main
  with:
    comment-pr: true
    claude-api-key: ${{ secrets.CLAUDE_API_KEY }}
    # 排除特定目录
    exclude-directories: "vendor,third_party,generated"
    # 自定义误报过滤指令
    false-positive-filtering-instructions: "./security/filter-rules.txt"
    # 自定义扫描指令
    custom-security-scan-instructions: "./security/scan-rules.txt"
    # 指定模型（默认 Opus 4.1）
    claude-model: "claude-opus-4-1-20250805"
```

也可以把 `security-review.md` 复制到项目的 `.claude/commands/` 目录下，定制本地 `/security-review` 命令的行为。

## ⚠️ 注意事项

1. **密钥不要硬编码** — 让 Claude Code 用 `${{ secrets.* }}`，绝不要把真实密钥写进配置
2. **别让 Claude Code 看你的密钥** — 粘贴日志时先检查有没有敏感信息
3. **测试环境先验证** — 新配置先在测试项目上跑，确认没问题再合并
4. **关注超时设置** — Claude Code 生成的配置有时会漏掉超时，记得补上
5. **安全审查的 PR 权限** — GitHub Action 的 `pull-requests: write` 权限仅用于评论，不会修改代码
6. **只审查可信 PR** — 官方建议配置"Require approval for all external contributors"，防止来自 fork 的注入攻击

## 🎓 学到了什么

1. **描述项目结构比描述 CI 语法更有效** — Claude Code 知道各种 CI 平台的语法
2. **多环境部署的关键是 rules/if 条件** — 让 Claude Code 帮你理清分支和环境的对应关系
3. **修复 CI 失败最有效的方式是直接贴日志** — 让它分析比你自己翻日志快
4. **安全扫描应该作为 CI 的标配步骤** — 别等项目上线了才发现漏洞
5. **Claude Code Security 是安全审查的范式转变** — 从模式匹配到语义理解，从高误报到精准定位，从"有问题"到"为什么 + 怎么修"
