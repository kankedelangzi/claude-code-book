# 3.4 遗留代码改造

> 没有文档、没有测试、没人敢动的老代码，Claude Code 帮你摸清套路、逐步改造。

## 🎯 场景描述

遗留代码的特点：

- 没有文档，不知道"为什么这么做"
- 没有测试，改了怕出问题
- 逻辑绕来绕去，看不懂
- 变量名是 a、b、c

**Claude Code 可以帮你：理解代码 → 补充文档 → 编写测试 → 逐步重构。**

## ✨ 改造工作流

### Step 1：让 Claude Code 读懂代码

```
帮我分析这个文件：
1. 总结每个函数的作用
2. 画出数据流向（输入什么、输出什么）
3. 找出关键的决策点（if/else 的逻辑）
4. 标出看不懂的地方，我来解释
```

**输出示例：**

```markdown
## 文件分析：order-service.js

### 函数清单
- `processOrder()` - 主处理函数，接收订单数据，调用下游服务
- `calcPrice()` - 计算订单价格，考虑折扣和会员等级
- `sendNotification()` - 发送订单通知（邮件/短信）
- `validateOrder()` - 验证订单合法性

### 数据流向
用户提交 → validateOrder → calcPrice → 保存数据库 → sendNotification → 返回

### 关键决策点
- 折扣：会员 9 折，订单 > 1000 再减 50
- 通知：vip 用户发邮件，普通用户发短信
- 状态：支付成功 → 配货中 → 已发货 → 已完成

### 不确定的地方
- `syncStock()` 这个函数看起来没用到？
- `retryCount` 是用来干什么的？
```

### Step 2：补充文档和注释

```
在每个函数上方添加 JSDoc 注释：
- @param: 参数说明
- @returns: 返回值说明
- @throws: 可能抛出的异常
- 简单描述函数的作用
```

**输出示例：**

```javascript
/**
 * 处理订单主流程
 * @param {Object} orderData - 订单数据，包含 items、customerId、paymentInfo
 * @returns {Promise<{orderId: string, total: number}>} 处理结果
 * @throws {ValidationError} 订单数据不合法
 * @throws {PaymentError} 支付失败
 */
async function processOrder(orderData) {
  // ...
}
```

### Step 3：编写测试

**先问清楚边界条件：**

```
这个函数有哪些边界情况需要测试？
1. 正常情况
2. 边界值（空数组、零值、最大值）
3. 异常情况（参数缺失、类型错误）
4. 并发情况（如果有共享状态）
```

**然后生成测试：**

```
为 calcPrice 函数生成 Jest 测试：
- 用 describe/it 结构
- 覆盖所有你说的边界情况
- 用 test.each 做参数化测试
```

**输出示例：**

```javascript
describe('calcPrice', () => {
  describe('正常情况', () => {
    it('基本价格计算', () => {
      const items = [{ price: 100, quantity: 2 }];
      expect(calcPrice(items, false)).toBe(200);
    });
  });

  describe('折扣', () => {
    it('会员打9折', () => {
      const items = [{ price: 100, quantity: 1 }];
      expect(calcPrice(items, true)).toBe(90);
    });

    it('订单超过1000再减50', () => {
      const items = [{ price: 500, quantity: 2 }];
      expect(calcPrice(items, false)).toBe(950); // 1000 - 50
    });
  });

  describe('边界情况', () => {
    it('空数组返回0', () => {
      expect(calcPrice([], false)).toBe(0);
    });

    it('数量为0返回0', () => {
      const items = [{ price: 100, quantity: 0 }];
      expect(calcPrice(items, false)).toBe(0);
    });
  });
});
```

### Step 4：逐步重构

**从小处开始，一次只改一件事：**

```
这个文件我想分几步重构：

第一步（这次）：
- 把 a、b、c 这样的变量名改成有意义的名称
- 其他不改

请只做这步，改完我跑测试验证。
```

```
第二步（这次）：
- 把这个 200 行的函数拆成几个小函数
- 保持输入输出不变
- 其他不改
```

```
第三步（这次）：
- 提取魔法数字（1000、50、0.9）为常量
- 用常量名替代
```

**不要一次想把所有问题都改掉——容易出 bug，难以定位问题。**

## 🔍 遗留代码常见问题处理

### 问题 1：全局变量满天飞

```javascript
// 重构前
let currentUser = null;
let orderCache = {};

function login(u, p) { currentUser = u; }
function getOrder() { return orderCache[currentUser.id]; }
```

**重构指令：**

```
把全局变量 currentUser 和 orderCache 改成参数传递。
如果需要共享状态，用一个 context 对象包裹。
```

---

### 问题 2：深嵌套回调

```javascript
// 重构前
function getData(id, callback) {
  db.get(id, function(err, data) {
    if (err) callback(err);
    else {
      process(data, function(err, result) {
        if (err) callback(err);
        else save(result, callback);
      });
    }
  });
}
```

**重构指令：**

```
把这个回调风格改成 async/await。
保持相同的输入输出和错误处理逻辑。
```

---

### 问题 3：字符串拼接 SQL

```javascript
// 重构前
const sql = "SELECT * FROM users WHERE id = " + userId + " AND status = '" + status + "'";
```

**重构指令：**

```
改成参数化查询，防止 SQL 注入：
- 用 ? 占位符
- 传入参数数组
- 保持查询逻辑不变
```

**重构后：**

```javascript
const sql = "SELECT * FROM users WHERE id = ? AND status = ?";
const result = await db.query(sql, [userId, status]);
```

---

### 问题 4：重复代码

**重构指令：**

```
这个文件有多处重复的验证逻辑：
- validateEmail()
- validatePhone()
- validatePassword()

把它们提取成一个通用的 validate(value, rules) 函数，
支持配置化规则（必填、格式、最小长度等）。
```

## 🛡️ 遗留代码改造安全手册

| 原则 | 做法 |
|------|------|
| **先测后改** | 用 git stash 暂存，改完 pop 回去对比 |
| **小步提交** | 每个小改动单独 commit，标记 "refactor(legacy): ..." |
| **对比测试** | 改前改后跑相同的测试，确认结果一致 |
| **保留历史** | 不要一次性删除旧代码，用注释标记废弃 |
| **有记录** | 记录踩的坑和做的决策，补充到代码注释 |

## 🔥 实战案例：Python 遗留项目改造

### 项目背景

一个 3 年前写的 Flask 内部工具，没人维护，新需求要加功能：

```python
# app.py - 800行的单文件应用
app = Flask(__name__)
app.config['SQLALCHEMY_DATABASE_URI'] = 'mysql://root:123456@localhost/old_db'

@app.route('/users')
def get_users():
    d = request.args.get('dept')
    if d:
        r = db.execute('SELECT * FROM users WHERE dept="' + d + '"')
    else:
        r = db.execute('SELECT * FROM users')
    result = []
    for i in r:
        result.append({'name': i[1], 'age': i[2], 'dept': i[3]})
    return jsonify(result)

@app.route('/users', methods=['POST'])
def add_user():
    n = request.form.get('name')
    a = request.form.get('age')
    d = request.form.get('dept')
    db.execute('INSERT INTO users (name,age,dept) VALUES ("'+n+'","'+a+'","'+d+'")')
    return 'ok'

# ... 还有 700 行类似风格的代码
```

**问题清单：**
1. 🔴 SQL 注入漏洞（字符串拼接）
2. 🔴 数据库密码硬编码
3. 🟡 变量名单字母，看不懂
4. 🟡 800行单文件，无法维护
5. 🟡 没有测试、没有错误处理

### Step 1：让 Claude Code 全面分析

```
分析 app.py 这个文件，给我：
1. 安全漏洞清单（按严重程度排序）
2. 代码结构建议（怎么拆分文件）
3. 需要优先修复的前 3 个问题
4. 改造路线图（从最安全到最有风险）
```

**Claude Code 输出：**

```markdown
## 安全漏洞
1. 🔴 SQL 注入（6处字符串拼接 SQL）
2. 🔴 数据库密码硬编码
3. 🟡 没有输入验证
4. 🟡 没有 CORS 配置

## 改造路线图
Phase 1：修复安全问题（SQL注入 + 密码硬编码）← 先做这个
Phase 2：拆分文件结构（MVC 分层）
Phase 3：添加错误处理和输入验证
Phase 4：编写测试
Phase 5：添加类型提示
```

### Step 2：修复安全问题

```
第一步：修复所有 SQL 注入问题。

把所有字符串拼接的 SQL 改成参数化查询，用 ? 占位符。
保持逻辑不变，只改安全相关的部分。
```

**修改前：**
```python
r = db.execute('SELECT * FROM users WHERE dept="' + d + '"')
db.execute('INSERT INTO users (name,age,dept) VALUES ("'+n+'","'+a+'","'+d+'")')
```

**修改后：**
```python
r = db.execute('SELECT * FROM users WHERE dept = ?', (d,))
db.execute('INSERT INTO users (name, age, dept) VALUES (?, ?, ?)', (n, a, d))
```

```
第二步：把硬编码的数据库密码移到环境变量。

用 python-dotenv 从 .env 文件读取配置。
```

**修改后：**
```python
from dotenv import load_dotenv
load_dotenv()

app.config['SQLALCHEMY_DATABASE_URI'] = os.environ.get('DATABASE_URL')
```

### Step 3：拆分文件结构

```
把 app.py 拆成 MVC 结构：
- app.py - Flask 应用初始化和路由注册
- models/ - 数据模型
- routes/ - 路由处理（按功能分文件）
- services/ - 业务逻辑
- config.py - 配置

每个文件的内容从 app.py 提取，保持功能不变。
```

**拆分后的目录结构：**

```
project/
├── app.py              # Flask 入口
├── config.py           # 配置管理
├── models/
│   └── user.py         # User 模型
├── routes/
│   ├── __init__.py
│   └── user_routes.py  # 用户相关路由
├── services/
│   └── user_service.py # 用户业务逻辑
├── tests/
│   └── test_user.py    # 测试
└── .env                # 环境变量
```

### Step 4：添加测试和类型提示

```
为 routes/user_routes.py 编写 pytest 测试：
- 使用 Flask test client
- 覆盖 GET /users 和 POST /users
- 包含正常情况和异常情况
```

**测试代码：**

## 🧩 更多遗留代码模式及改造指令

### 问题 5：配置硬编码

```python
# 改造前
API_URL = 'https://api.example.com/v1'
TIMEOUT = 30
MAX_RETRIES = 3

def fetch_data():
    return requests.get(API_URL, timeout=TIMEOUT)
```

**重构指令：**

```
把所有硬编码配置提取到 .env 文件和 config 类中：
1. 创建 .env 文件存放环境变量
2. 创建 config.py 用 pydantic-settings 管理配置
3. 原代码改为从 config 读取
4. 添加默认值和类型验证
```

**改造后：**

```python
# config.py
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    api_url: str = 'https://api.example.com/v1'
    timeout: int = 30
    max_retries: int = 3

    class Config:
        env_file = '.env'

settings = Settings()

# 使用处
import requests
from config import settings

def fetch_data():
    return requests.get(settings.api_url, timeout=settings.timeout)
```

### 问题 6：异常被吞掉

```python
# 改造前
try:
    result = do_something()
except:
    pass  # 吞掉所有异常
```

**重构指令：**

```
修复所有 bare except:
1. 至少捕获具体异常（Exception 而非裸 except）
2. 添加日志记录
3. 需要时向上传播或返回错误信息
```

**改造后：**

```python
import logging
logger = logging.getLogger(__name__)

try:
    result = do_something()
except ValueError as e:
    logger.error(f'参数错误: {e}')
    raise  # 向上传播
except Exception as e:
    logger.exception(f'处理失败: {e}')
    return {'error': str(e)}
```

### 问题 7：回调地狱（Python 版）

```python
# 改造前：嵌套回调
def get_user(user_id, callback):
    db.find('users', user_id, lambda err, user:
        get_orders(user.id, lambda err, orders:
            calc_total(orders, lambda err, total:
                callback(user, orders, total)
            )
        )
    )
```

**重构指令：**

```
把嵌套回调改成 async/await 风格：
```python

async def get_user_info(user_id):
    user = await db.find('users', user_id)
    orders = await get_orders(user.id)
    total = await calc_total(orders)
    return user, orders, total
```

## 📊 遗留代码改造决策矩阵

遇到遗留代码时，怎么决定「改还是不改」？

| 情况 | 建议 | 理由 |
|------|------|------|
| 代码有安全漏洞 | **必须改** | 安全是底线 |
| 代码需要加新功能 | **先加测试再改** | 测试是安全网 |
| 代码只是难看但运行正常 | **可以不改** | 如果没 bug 不要碰 |
| 代码有性能问题 | **profile 后再改** | 先确认瓶颈在哪 |
| 代码下周要给别人维护 | **加文档和注释** | 让下一个人能看懂 |
| 代码只有你一个人看 | **加 TODO 标记** | 有空再改，先标记 |

## 📝 小结

改造遗留代码的核心：

1. **先理解，再动手** — 花时间看懂代码，比盲目改更值
2. **文档即测试** — 写注释的过程就是理清思路的过程
3. **测试是护身符** — 没有测试的重构是裸奔
4. **小步快跑** — 一次只改一个问题，改完就验证
5. **安全优先** — SQL 注入和密码泄露必须最先修
6. **别追求完美** — 能跑的烂代码 > 跑不起来的好代码

**改造遗留代码是一场马拉松，不是百米冲刺。保持耐心，稳步前进。**
