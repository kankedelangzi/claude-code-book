你写完了一段代码，但不确定：

## ✨ 案例1：发现隐藏的 Bug

### 场景

你写了一个用户注册接口，功能测试都通过了，但你总觉得哪里不对。

### 有问题的代码

```javascript
// routes/users.js
app.post('/api/users', async (req, res) => {
  const { name, email, password } = req.body;

  // 检查邮箱是否已存在
  const existing = await User.findOne({ email });
  if (existing) {
    return res.status(400).json({ error: '邮箱已被注册' });
  }

  // 创建用户
  const user = new User({
    name,
    email,
    password: md5(password) // 用 MD5 哈希密码
  });

  await user.save();

  // 返回用户信息
  res.json({
    id: user._id,
    name: user.name,
    email: user.email,
    password: user.password  // 顺便返回密码哈希
  });
});
```

### Claude Code 审查

```
请审查 routes/users.js 中的 POST /api/users 接口，
重点关注安全性问题，给出具体修复代码。
```

### Claude Code 发现的问题

| # | 问题 | 严重程度 | 说明 |
|---|------|---------|------|
| 1 | MD5 哈希密码 | 🔴 高 | MD5 可被彩虹表快速破解，应用 bcrypt |
| 2 | 返回密码哈希 | 🔴 高 | 响应中不应包含任何密码信息 |
| 3 | 无输入验证 | 🟡 中 | name/email/password 未验证格式和长度 |
| 4 | 竞态条件 | 🟡 中 | 检查邮箱和创建用户之间有时间窗口 |
| 5 | 无错误处理 | 🟡 中 | 数据库操作缺少 try/catch |

### 修复后的代码

```javascript
// routes/users.js — 修复版
app.post('/api/users', async (req, res) => {
  try {
    const { name, email, password } = req.body;

    // 输入验证
    if (!name || name.length < 2 || name.length > 50) {
      return res.status(400).json({ error: '姓名长度需在2-50之间' });
    }
    if (!email || !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(email)) {
      return res.status(400).json({ error: '邮箱格式不正确' });
    }
    if (!password || password.length < 8) {
      return res.status(400).json({ error: '密码至少8位' });
    }

    // 检查邮箱（加索引防并发）
    const existing = await User.findOne({ email });
    if (existing) {
      return res.status(409).json({ error: '邮箱已被注册' });
    }

    // 用 bcrypt 哈希密码
    const hashedPassword = await bcrypt.hash(password, 10);

    const user = new User({
      name,
      email,
      password: hashedPassword
    });

    await user.save();

    // 不返回密码
    res.status(201).json({
      id: user._id,
      name: user.name,
      email: user.email
    });
  } catch (err) {
    console.error('注册失败:', err);
    res.status(500).json({ error: '服务器错误' });
  }
});
```

### 效率对比

| 指标 | 人工审查 | Claude Code 审查 |
|------|---------|-----------------|
| 耗时 | 30-60 分钟 | 1-2 分钟 |
| 遗漏风险 | 中（尤其安全项） | 低（系统化检查） |
| 修复建议 | 需另查文档 | 直接给代码 |

## ✨ 案例2：性能审查——找出 N+1 查询

### 场景

一个文章列表页面加载越来越慢，数据量一大就卡。

### 有问题的代码

```javascript
// routes/articles.js
app.get('/api/articles', async (req, res) => {
  const articles = await Article.find().sort({ createdAt: -1 });

  // 给每篇文章加上作者信息和评论数
  const result = await Promise.all(articles.map(async (article) => {
    const author = await User.findById(article.authorId);
    const commentCount = await Comment.countDocuments({ articleId: article._id });
    return {
      ...article.toObject(),
      authorName: author.name,
      commentCount
    };
  }));

  res.json(result);
});
```

### Claude Code 审查

```
分析 routes/articles.js 中 GET /api/articles 的性能问题，
特别关注数据库查询效率，给出优化方案。
```

### 发现的问题

**N+1 查询问题**：每篇文章查 2 次数据库（1 次作者 + 1 次评论数），100 篇文章就是 201 次查询。

### 优化后的代码

```javascript
// routes/articles.js — 优化版
app.get('/api/articles', async (req, res) => {
  const articles = await Article.find()
    .sort({ createdAt: -1 })
    .limit(50);  // 分页

  // 批量获取所有作者
  const authorIds = [...new Set(articles.map(a => a.authorId))];
  const authors = await User.find({ _id: { $in: authorIds } });
  const authorMap = new Map(authors.map(a => [a._id.toString(), a]));

  // 批量获取评论数
  const commentCounts = await Comment.aggregate([
    { $match: { articleId: { $in: articles.map(a => a._id) } } },
    { $group: { _id: '$articleId', count: { $sum: 1 } } }
  ]);
  const countMap = new Map(commentCounts.map(c => [c._id.toString(), c.count]));

  const result = articles.map(article => ({
    ...article.toObject(),
    authorName: authorMap.get(article.authorId.toString())?.name || '未知',
    commentCount: countMap.get(article._id.toString()) || 0
  }));

  res.json(result);
});
```

### 性能对比

| 数据量 | 优化前查询次数 | 优化后查询次数 | 耗时变化 |
|--------|-------------|-------------|---------|
| 10 篇 | 21 次 | 3 次 | ~70%↓ |
| 50 篇 | 101 次 | 3 次 | ~90%↓ |
| 100 篇 | 201 次 | 3 次 | ~95%↓ |

## ✨ 案例3：安全审查——发现注入漏洞

### 场景

一个搜索接口，产品经理要求支持模糊搜索。

### 有问题的代码

```python
# routes/search.py
@app.get("/api/search")
async def search_articles(q: str):
    # 直接拼接 SQL
    query = f"SELECT * FROM articles WHERE title LIKE '%{q}%' OR content LIKE '%{q}%'"
    results = await db.execute(query)
    return [{"id": r.id, "title": r.title} for r in results]
```

### Claude Code 审查

```
审查 routes/search.py 的搜索接口，重点检查 SQL 注入风险，
演示攻击方式并给出安全实现。
```

### 发现的漏洞

**SQL 注入**：攻击者输入 `' UNION SELECT password FROM admins--` 即可获取管理员密码。

### 修复代码

```python
# routes/search.py — 安全版
@app.get("/api/search")
async def search_articles(q: str):
    # 使用参数化查询
    pattern = f"%{q}%"
    query = "SELECT * FROM articles WHERE title LIKE ? OR content LIKE ?"
    results = await db.execute(query, pattern, pattern)
    return [{"id": r.id, "title": r.title} for r in results]
```

## ✨ 案例4：TypeScript 类型安全审查

### 场景

你的 TypeScript 项目虽然用了 TS，但到处都是 `any`，类型安全形同虚设。

### 有问题的代码

```typescript
// utils/format.ts
function formatData(data: any): any {
  const result: any = {};
  for (const key in data) {
    if (typeof data[key] === 'string') {
      result[key] = data[key].trim();
    } else if (typeof data[key] === 'number') {
      result[key] = data[key].toFixed(2);
    } else {
      result[key] = data[key];
    }
  }
  return result;
}
```

### Claude Code 审查

```
审查 utils/format.ts，重点检查 TypeScript 类型安全问题：
1. 消除所有 any
2. 添加泛型支持
3. 确保类型推断正确
给出重构后的完整代码。
```

### 修复后的代码

```typescript
// utils/format.ts — 类型安全版
type FormattableValue = string | number | boolean | null;

type FormatResult<T> = {
  [K in keyof T]: T[K] extends string ? string
    : T[K] extends number ? string
    : T[K];
};

function formatData<T extends Record<string, FormattableValue>>(
  data: T
): FormatResult<T> {
  const result = {} as FormatResult<T>;

  for (const key in data) {
    const value = data[key];
    if (typeof value === 'string') {
      (result as any)[key] = value.trim();
    } else if (typeof value === 'number') {
      (result as any)[key] = value.toFixed(2);
    } else {
      (result as any)[key] = value;
    }
  }

  return result;
}

// 使用示例 — 类型自动推断
const input = { name: '  hello  ', price: 99.9, active: true };
const formatted = formatData(input);
// formatted.name: string (已 trim)
// formatted.price: string (已 toFixed)
// formatted.active: boolean (原样)
```

## 🚀 质量保证工作流

```
1. 代码完成
   └── 功能实现 + 基本自测

2. Claude Code 审查
   ├── 安全审查（每次必做）
   ├── 性能审查（涉及数据库/IO 时必做）
   └── 代码质量审查（PR 提交前做）

3. 修复问题
   ├── 按严重程度排序
   ├── 先修安全，再修 Bug，再优化
   └── 修完后重新审查确认

4. 提交代码
   └── git commit -m "fix: [描述审查修复的问题]"
```

### 工作流自动化技巧

在 `CLAUDE.md` 中加入审查规则，让每次交互都自动考虑：

```markdown
## 代码审查规则
- 所有涉及用户输入的代码必须做验证
- 所有数据库查询必须使用参数化
- 密码必须用 bcrypt 哈希，禁止 MD5/SHA1
- API 响应禁止包含密码、token 等敏感信息
- 数据库查询超过 3 次的接口需考虑批量优化
```

## 📝 小结

Claude Code 代码审查的核心优势：

- **快速系统化** — 1-2 分钟完成人工 30-60 分钟的审查
