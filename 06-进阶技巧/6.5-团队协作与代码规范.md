# 6.5 团队协作与代码规范

> 让 Claude Code 帮助团队保持代码一致性，提高协作效率。

## 🎯 场景描述

团队协作中经常遇到：
- 代码风格不统一——有人用 tab 有人用空格
- 命名规范不一致——驼峰和下划线混用
- 项目结构混乱——新成员看不懂目录
- 文档缺失——谁也不知道怎么跑起来

**Claude Code 可以帮团队建立和维护代码规范，自动检查和修复风格问题，让代码像一个人写的。**

---

## ✨ 案例1：从混乱到统一——项目规范化

### 场景

你接手了一个 3 人开发的项目，代码风格一言难尽：

```javascript
// 张三的风格
var get_user_info = function(userId) {
    return db.query("SELECT * FROM users WHERE id = " + userId);
}

// 李四的风格
const getUserInfo = (userId) => {
  return db.query('SELECT * FROM users WHERE id = ?', [userId])
}

// 王五的风格
function userInfo(id){
    let sql = `select * from users where id=${id}`;
    return db.execute(sql);
}
```

三种风格，三种习惯，还有 SQL 注入风险。

### Claude Code 统一规范

```
分析这个项目中所有的代码风格问题：
1. 列出所有不一致的地方
2. 制定统一的代码规范
3. 生成 ESLint + Prettier 配置
4. 批量修复所有文件
```

### 生成的配置文件

```javascript
// .eslintrc.js
module.exports = {
  env: { node: true, es2024: true },
  extends: ['eslint:recommended'],
  parserOptions: { ecmaVersion: 'latest', sourceType: 'module' },
  rules: {
    'no-var': 'error',              // 禁止 var
    'prefer-const': 'error',         // 优先 const
    'no-template-curly-in-string': 'error', // 检测模板字符串误用
    'camelcase': ['error', {         // 驼峰命名
      properties: 'always',
      ignoreDestructuring: false
    }],
    'no-eval': 'error',
    'no-implied-eval': 'error',
    'security/detect-non-literal-regexp': 'warn',
    'security/detect-object-injection': 'warn'
  }
};
```

```json
// .prettierrc
{
  "singleQuote": true,
  "semi": true,
  "tabWidth": 2,
  "trailingComma": "es5",
  "printWidth": 100
}
```

```ini
// .editorconfig — 让所有编辑器统一
root = true

[*]
indent_style = space
indent_size = 2
end_of_line = lf
charset = utf-8
trim_trailing_whitespace = true
insert_final_newline = true
```

### 修复后的统一代码

```javascript
// 统一后——张三、李四、王五的代码变成同一风格
const getUserInfo = (userId) => {
  return db.query('SELECT * FROM users WHERE id = ?', [userId]);
};
```

## ✨ 案例2：用 CLAUDE.md 建立团队约定

### 场景

团队 5 个人都在用 Claude Code，但每个人给 Claude 的指令不一样，导致生成的代码风格也不同。

### 解决方案：项目级 CLAUDE.md

```markdown
# CLAUDE.md — 团队项目约定

## 技术栈
- 后端：Node.js + Express + Prisma
- 数据库：PostgreSQL
- 前端：React + TypeScript + Tailwind CSS
- 测试：Vitest + Testing Library

## 代码规范
- 使用 const，禁止 var
- 函数使用箭头函数
- 命名：驼峰（变量/函数），帕斯卡（类/组件）
- 所有 API 路由必须有错误处理
- 数据库操作必须用 Prisma，禁止原始 SQL
- 所有接口必须有 TypeScript 类型定义

## 文件结构
- routes/ — 路由定义
- services/ — 业务逻辑
- middleware/ — 中间件
- prisma/ — 数据库相关
- __tests__/ — 测试文件

## Git 规范
- 提交格式：type(scope): description
- type: feat/fix/docs/refactor/test/chore
- 分支：main/develop/feature-xxx/hotfix-xxx

## 安全规则
- 密码用 bcrypt 哈希
- 所有用户输入必须验证
- 响应中不返回敏感信息
- 使用参数化查询

## 测试要求
- 新接口必须有单元测试
- 关键业务必须有集成测试
- 测试覆盖率目标：80%
```

### 效果

每个人用 Claude Code 时，Claude 自动遵守这些规则，不需要每次重复说明。

## ✨ 案例3：Git 提交规范化

### 场景

团队的 git log 是这样的：

```
fix bug
update
修改了一下
aaaa
测试
final fix
final final fix
```

### Claude Code 规范化提交

```
分析当前的改动，按照 Conventional Commits 规范生成提交信息：
格式：type(scope): description

type 可选：feat/fix/docs/style/refactor/perf/test/chore
scope 可选：api/ui/db/auth 等

只写提交信息，不要多余解释。
```

### 生成结果

```bash
# 之前
$ git commit -m "fix bug"

# 之后
$ git commit -m "fix(auth): resolve token expiration edge case on refresh"
$ git commit -m "feat(api): add pagination to GET /users endpoint"
$ git commit -m "refactor(db): replace raw SQL with Prisma queries in user service"
```

### 配合 Git Hook 自动化

```bash
# 安装 commitlint + husky
npm install --save-dev @commitlint/cli @commitlint/config-conventional husky
npx husky init
echo 'npx --no -- commitlint --edit "$1"' > .husky/commit-msg
```

```javascript
// commitlint.config.js
module.exports = {
  extends: ['@commitlint/config-conventional'],
  rules: {
    'type-enum': [2, 'always', [
      'feat', 'fix', 'docs', 'style', 'refactor', 'perf', 'test', 'chore'
    ]],
    'scope-case': [2, 'always', 'lower-case'],
    'subject-max-length': [2, 'always', 72]
  }
};
```

## ✨ 案例4：代码审查清单自动化

### 场景

团队 code review 经常遗漏关键检查项，每次审查标准不一样。

### Claude Code 生成审查清单

```
基于项目的技术栈和 CLAUDE.md 中的规范，
生成一份代码审查清单，格式为 Markdown 表格。
```

### 生成的审查清单

```markdown
## Code Review Checklist

### 必须（阻断合并）
- [ ] 所有用户输入已验证
- [ ] 数据库操作使用参数化查询
- [ ] API 有错误处理和合适的 HTTP 状态码
- [ ] 无硬编码密钥或敏感信息
- [ ] 新接口有 TypeScript 类型定义

### 推荐（建议改进）
- [ ] 函数单一职责，不超过 30 行
- [ ] 复杂逻辑有注释说明
- [ ] 错误信息对用户友好（不暴露内部细节）
- [ ] 有对应的单元测试
- [ ] 遵循 CLAUDE.md 中的命名规范

### 可选（锦上添花）
- [ ] 考虑了边界情况和异常场景
- [ ] 接口向后兼容
- [ ] 添加了性能相关的注释
```

### 在 PR 模板中集成

```markdown
<!-- .github/PULL_REQUEST_TEMPLATE.md -->
## 变更描述
<!-- 简述改了什么 -->

## 审查清单
- [ ] 安全检查通过（见审查清单）
- [ ] 测试通过
- [ ] CLAUDE.md 规范遵守
- [ ] 无不相关的改动

## 截图/测试结果
<!-- 如果是 UI 变更，贴截图 -->
```

## 🚀 团队协作工作流

```
1. 项目初始化
   ├── 生成 CLAUDE.md（项目约定）
   ├── 配置 ESLint + Prettier + EditorConfig
   ├── 安装 Husky + Commitlint
   └── 生成 PR 模板和审查清单

2. 日常开发
   ├── Claude Code 自动遵守 CLAUDE.md 规范
   ├── 提交时 Husky 检查格式
   └── PR 时对照审查清单

3. 持续改进
   ├── 定期更新 CLAUDE.md
   ├── 根据新问题补充审查清单
   └── 优化工具配置
```

---

## ⚠️ 团队协作注意事项

| 事项 | 说明 |
|------|------|
| **规范先行** | 项目一开始就定规范，越晚越痛苦 |
| **工具 > 说服** | 用自动化工具强制规范，别靠嘴说 |
| **CLAUDE.md 很重要** | 这是团队和 Claude Code 的共同约定 |
| **渐进式推进** | 先加核心规范，再逐步完善 |
| **团队共识** | 规范要讨论通过，不能一人拍板 |

---

## 📝 小结

Claude Code 在团队协作中的核心价值：

- **CLAUDE.md = 团队共识** — 让所有人和 AI 都遵守同一套规则
- **自动规范化** — 批量修复风格，生成配置文件
- **代码审查加速** — 自动检查清单项，减少人工遗漏
- **文档不缺失** — 几分钟生成完整协作文档

**好的代码规范是团队效率的基础，Claude Code 让制定和执行规范变得简单。先把规矩立起来，再让工具帮你守规矩。**
