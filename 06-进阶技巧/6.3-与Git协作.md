# 6.3 与 Git 协作

> 让 Claude Code 成为你的 Git 副驾驶——提交、分支、冲突、审查，全流程自动化。

## 🎯 场景描述

Git 操作繁琐又容易出错：
- 提交信息不知道怎么写，最后全是 "fix bug" 和 "update"
- 代码改了一堆，不知道分几次提交
- 合并冲突看得眼花，解决完又引入新 bug
- PR 描述懒得写，同事 review 一头雾水

Claude Code 不仅能帮你执行 Git 命令，更能理解你的代码改动，给出专业建议。

## 💡 核心思路

```
不是让 Claude Code 替你敲 git 命令，而是让它理解代码变更的语义，做出和人一样的判断
```

## 📝 实战案例一：生成 Commit Message

### 需求描述

```
帮我看看改了什么，写个 commit message
```

### Claude Code 执行

```bash
git diff --stat
```

```
 src/api/users.ts    |  12 +++++++++--
 src/services/auth.ts |  5 ++--
 tests/users.test.ts  |  8 +++++++
 3 files changed, 21 insertions(+), 4 deletions(-)
```

Claude Code 不只是看文件名，它会深入阅读 diff 内容：

```bash
git diff
```

```diff
+interface User {
+  id: string;
+  name: string;
+  role: 'admin' | 'user' | 'guest';  // 新增角色字段
+}
+
+function validateRole(role: string): boolean {
+  return ['admin', 'user', 'guest'].includes(role);
+}
```

### 生成的 Commit Message

```
feat: 添加用户角色字段，优化认证逻辑

- User 接口增加 role 字段（admin/user/guest）
- authService 支持角色验证
- 新增用户角色相关测试用例
```

**为什么比你自己写的好？**

因为它读了每一行 diff，理解了改动的意图，而不只是看文件名凑描述。

### Conventional Commits 速查

| 类型 | 用途 | 示例 |
|------|------|------|
| `feat:` | 新功能 | `feat: 添加用户角色字段` |
| `fix:` | Bug 修复 | `fix: 修复登录超时未重定向` |
| `docs:` | 文档更新 | `docs: 更新 API 接口说明` |
| `refactor:` | 重构 | `refactor: 抽取认证逻辑为独立模块` |
| `test:` | 测试 | `test: 添加角色验证单元测试` |
| `chore:` | 杂务 | `chore: 升级依赖版本` |
| `perf:` | 性能 | `perf: 优化列表分页查询` |

## 📝 实战案例二：智能分批提交

### 需求描述

```
我改了很多文件，帮我按功能分批提交
```

### Claude Code 分析

```
发现 11 个文件改动，分析如下：

📦 功能分组建议：

1️⃣ 认证相关（3 个文件）
   - src/services/auth.ts      → 角色验证逻辑
   - src/middleware/auth.ts     → 角色权限中间件
   - src/types/auth.ts         → 认证类型定义

2️⃣ 用户 API（3 个文件）
   - src/api/users.ts          → 用户角色字段
   - src/types/user.ts         → User 类型更新
   - src/utils/role.ts         → 角色工具函数

3️⃣ 数据库迁移（2 个文件）
   - prisma/migrations/...     → 新增 role 列
   - prisma/seed.ts            → 角色种子数据

4️⃣ 测试（3 个文件）
   - tests/auth.test.ts
   - tests/users.test.ts
   - tests/role.test.ts

请选择：
A. 按分组分 4 次提交（推荐）
B. 合并数据库和 API 为一次，分 3 次提交
C. 全部一次提交
D. 自定义分组
```

### 选择 A，Claude Code 依次执行

```bash
# 第一批：认证
git add src/services/auth.ts src/middleware/auth.ts src/types/auth.ts
git commit -m "feat(auth): 添加角色验证逻辑和权限中间件"

# 第二批：用户 API
git add src/api/users.ts src/types/user.ts src/utils/role.ts
git commit -m "feat(users): 用户 API 支持角色字段"

# 第三批：数据库
git add prisma/
git commit -m "feat(db): 添加用户角色列和种子数据"

# 第四批：测试
git add tests/
git commit -m "test: 添加认证、用户角色、角色工具测试用例"
```

**分批提交的好处：**

- 出了问题可以精准 `git revert` 某一次提交
- Code review 按功能看，不用一次审几百行
- `git bisect` 定位 bug 时粒度更细

## 📝 实战案例三：解决合并冲突

### 需求描述

```
合并 dev 分支到 main，有冲突，帮我解决
```

### Claude Code 执行

```bash
git merge dev
```

```
CONFLICT (content): Merge conflict in src/config.ts
CONFLICT (content): Merge conflict in src/utils/format.ts
Automatic merge failed; fix conflicts and then commit the result.
```

**冲突文件 1：src/config.ts**

```typescript
<<<<<<< HEAD
const API_URL = 'https://api.example.com';
const TIMEOUT = 5000;
=======
const API_URL = 'https://dev-api.example.com';
const MAX_RETRIES = 3;
>>>>>>> dev
```

Claude Code 的分析和解决方案：

```
冲突分析（src/config.ts）：

- HEAD（main）保留了 API_URL 和 TIMEOUT
- dev 修改了 API_URL 并新增了 MAX_RETRIES

意图判断：
- API_URL：dev 是开发环境地址，main 是生产地址
  → 应该用环境变量，不要硬编码
- TIMEOUT：main 独有，应该保留
- MAX_RETRIES：dev 新增，应该保留

解决方案：
const API_URL = process.env.API_URL || 'https://api.example.com';
const TIMEOUT = Number(process.env.TIMEOUT) || 5000;
const MAX_RETRIES = Number(process.env.MAX_RETRIES) || 3;
```

**冲突文件 2：src/utils/format.ts**

```typescript
<<<<<<< HEAD
export function formatDate(date: Date): string {
  return date.toLocaleDateString('zh-CN');
}
=======
export function formatDate(date: Date, format?: string): string {
  if (format === 'iso') return date.toISOString();
  return date.toLocaleDateString('zh-CN');
}
>>>>>>> dev
```

Claude Code 分析：

```
冲突分析（src/utils/format.ts）：

- HEAD：简单的日期格式化
- dev：增加了 format 参数，支持 ISO 格式输出

意图判断：dev 的改动是纯增强，不破坏兼容性
→ 直接采用 dev 的版本
```

全部解决后自动提交：

```bash
git add src/config.ts src/utils/format.ts
git commit -m "merge: 合并 dev 分支，解决冲突（环境变量+formatDate增强）"
```

**关键：Claude Code 不是简单地选"我们的"或"他们的"，而是理解代码语义后做出判断。**

## 📝 实战案例四：交互式变基（Interactive Rebase）

### 需求描述

```
我本地有 5 个提交还没 push，太乱了，帮我整理一下
```

### 查看提交历史

```bash
git log --oneline -5
```

```
e3f2a1 fix: 修了个 typo
a1b2c3 feat: 添加用户列表
d4e5f6 fix: 修复用户列表分页
g7h8i9 feat: 添加搜索功能
j0k1l2 chore: 临时调试代码
```

Claude Code 建议：

```
提交分析：
1. e3f2a1 "fix: 修了个 typo" → 可以 squash 到 a1b2c3
2. a1b2c3 "feat: 添加用户列表" → 保留
3. d4e5f6 "fix: 修复用户列表分页" → 可以 squash 到 a1b2c3
4. g7h8i9 "feat: 添加搜索功能" → 保留
5. j0k1l2 "chore: 临时调试代码" → 删除（drop）

建议操作：
- pick a1b2c3 feat: 添加用户列表
- squash d4e5f6 修复用户列表分页
- squash e3f2a1 修了个 typo
- pick g7h8i9 feat: 添加搜索功能
- drop j0k1l2 临时调试代码

整理后只需 2 个干净的提交。是否执行？
```

确认后执行变基，最终历史变得干净整洁。

## 📝 实战案例六：Git Hook 自动化

### 需求描述

```
帮我设置 pre-commit hook，提交前自动跑 lint 和格式化
```

### Claude Code 生成配置

**package.json（使用 lint-staged + husky）**

```json
{
  "lint-staged": {
    "*.{ts,tsx}": [
      "eslint --fix",
      "prettier --write"
    ],
    "*.{json,md}": [
      "prettier --write"
    ]
  },
  "scripts": {
    "prepare": "husky"
  }
}
```

```bash
# 安装依赖
npm install -D husky lint-staged

# 初始化 husky
npx husky init

# 创建 pre-commit hook
echo "npx lint-staged" > .husky/pre-commit
```

**更进一步：让 Claude Code 自动检查 commit message 格式**

```bash
# 创建 commit-msg hook
cat > .husky/commit-msg << 'EOF'
# 检查 commit message 是否符合 Conventional Commits
MSG=$(cat "$1")
PATTERN="^(feat|fix|docs|refactor|test|chore|perf|ci|build|revert)(\(.+\))?: .{1,80}"

if ! echo "$MSG" | grep -qE "$PATTERN"; then
  echo "❌ Commit message 格式不正确！"
  echo ""
  echo "正确格式：<type>(<scope>): <subject>"
  echo "示例：feat(auth): 添加角色验证中间件"
  echo ""
  echo "可用类型：feat|fix|docs|refactor|test|chore|perf|ci|build|revert"
  exit 1
fi
EOF
```

## ⚡ 技巧汇总

### 1. Git 别名 + Claude Code

```bash
# 智能 commit：让 Claude Code 生成 message
git config alias.ai-commit '!f() { 
  msg=$(claude "根据 git diff --cached 生成简洁的 commit message，只要一行，用 Conventional Commits 格式"); 
  git commit -m "$msg"; 
}; f'

# 使用
git add .
git ai-commit
```

### 2. 紧急撤回

```
刚才的提交有问题，帮我撤回但保留改动
```

Claude Code 会用 `git reset --soft HEAD~1` 而不是 `--hard`，确保代码不丢失。

### 3. 查找引入 Bug 的提交

```
这个 Bug 是什么时候引入的？帮我 bisect
```

Claude Code 会引导你完成 `git bisect` 流程，自动标记好坏提交，精准定位问题。

## 🎓 学到了什么

1. **Commit message 让 Claude Code 写**——它读得懂 diff，写得懂人话
2. **大改动分批提交**——出了问题能精准回滚，review 也轻松
3. **冲突解决自动化**——不是简单选边，而是理解语义后决策
4. **PR 描述让 Claude Code 整理**——专业、完整，还能提醒破坏性变更
5. **Git Hook + Changelog 自动化**——团队规范靠工具，不靠自觉

## ⚠️ 注意

- **重要操作先确认**：让 Claude Code 解释要做什么，确认后再执行
- **push 前检查**：推送到远程前看一眼改动是否正确
- **敏感文件别提交**：`.env`、密钥文件等确保在 `.gitignore` 中
- **变基有风险**：已推送的提交不要 rebase，会搞乱协作历史
