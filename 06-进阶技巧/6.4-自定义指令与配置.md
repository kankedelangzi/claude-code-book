# 6.4 自定义指令与配置

> 打造专属的 Claude Code——让它记住你的偏好、遵循你的规范、套用你的模板。

## 🎯 场景描述

每次对话都要重复说：
- "用 TypeScript，不要 any"
- "注释用中文"
- "错误处理用 try-catch"
- "React 组件用函数式写法"

这些是你的编码习惯，不该每次都教一遍。Claude Code 提供了三层配置体系，让你说一次，终身有效。

## 💡 核心思路

```
全局配置（个人偏好） + 项目配置（团队规范） + 模板/Prompt（复用套路） = 不用重复说话的 Claude Code
```

---

## 📝 方法一：用户级全局配置

### 配置文件位置

```
~/.claude/config.json       # 全局行为配置
~/.claude/instructions.md   # 全局自定义指令
```

### 自定义指令示例

**~/.claude/instructions.md**

```markdown
# 我的编码偏好

## 语言与风格
- 使用 TypeScript，严禁 any（除非确实无法推断类型）
- 变量命名用 camelCase，常量用 UPPER_SNAKE_CASE
- 注释用中文，代码用英文
- 函数必须有 JSDoc 注释（中文描述）

## 编程习惯
- 错误处理用 try-catch，不要吞掉异常
- 优先使用 async/await，避免 .then() 链式调用
- React 组件用函数式 + Hooks，不用 class
- 样式用 Tailwind CSS，避免 inline style
- 日期处理用 dayjs，不用 moment

## 禁止事项
- 不要用 var
- 函数超过 50 行要拆分
- 不要硬编码配置，用环境变量
- 不要在组件里直接调 API，走 hooks
```

### 效果

以后每次对话，Claude Code 都会默认遵循这些规则。你可以专注说"做什么"，不用再操心"怎么做"。

### config.json 示例

```json
{
  "model": "claude-sonnet-4-20250514",
  "permissions": {
    "allow": ["Bash(git*)", "Read", "Write"],
    "deny": ["Bash(rm -rf*)"]
  }
}
```

## 📝 方法二：项目级配置

### .claude 目录结构

```
project/
├── .claude/
│   ├── instructions.md       # 项目专属指令
│   ├── templates/            # 代码模板
│   │   ├── component.tsx
│   │   ├── api-handler.ts
│   │   └── test-file.test.ts
│   └── prompts/              # 常用 prompt
│       ├── review.md
│       └── test.md
├── src/
└── ...
```

### 项目指令示例

**.claude/instructions.md**

```markdown
# 项目规范

## 技术栈
- Next.js 14 (App Router) + TypeScript 5
- Prisma + PostgreSQL 15
- Tailwind CSS + shadcn/ui
- Jest + React Testing Library

## API 规范
- 路由格式：/api/v1/{resource}
- 响应格式：
  ```json
  {
    "success": true,
    "data": {},
    "error": null
  }
  ```
- 错误响应：
  ```json
  {
    "success": false,
    "data": null,
    "error": {
      "code": "AUTH_001",
      "message": "Token 已过期"
    }
  }
  ```

## 命名约定
- 组件：PascalCase → UserCard.tsx
- 函数/变量：camelCase → getUserById
- 文件：kebab-case → user-card.tsx
- 常量：UPPER_SNAKE_CASE → MAX_RETRY_COUNT
- 类型/接口：PascalCase + I前缀可选 → UserProfile

## 数据库
- Migration 必须可回滚（up + down）
- 字段命名用 snake_case
- 每张表有 created_at 和 updated_at
```

### 项目级 vs 用户级的优先级

```
项目级 .claude/instructions.md  >  用户级 ~/.claude/instructions.md
```

当两者冲突时，项目级优先。比如你个人偏好 Vue，但这个项目用 React，Claude Code 会跟着项目走。

## 📝 方法三：代码模板系统

### 模板的作用

团队协作最大的痛点不是"写不出代码"，而是"每个人写出来的代码风格不一样"。模板解决这个问题。

### 创建 React 组件模板

**.claude/templates/component.tsx**

```typescript
import { FC } from 'react';

interface {{ComponentName}}Props {
  className?: string;
  children?: React.ReactNode;
}

/**
 * {{ComponentName}} 组件
 *
 * @description {{Description}}
 */
export const {{ComponentName}}: FC<{{ComponentName}}Props> = ({
  className = '',
  children,
}) => {
  return (
    <div className={className}>
      {children}
    </div>
  );
};

export default {{ComponentName}};
```

### 创建 API Handler 模板

**.claude/templates/api-handler.ts**

```typescript
import { NextRequest, NextResponse } from 'next/server';

/**
 * {{Method}} {{Path}} 接口
 *
 * @description {{Description}}
 */
export async function {{Method}}{{ResourceName}}(
  request: NextRequest
) {
  try {
    // TODO: 实现业务逻辑

    return NextResponse.json({
      success: true,
      data: {},
      error: null,
    });
  } catch (error) {
    console.error('[{{ResourceName}}] Error:', error);

    return NextResponse.json(
      {
        success: false,
        data: null,
        error: {
          code: '{{RESOURCE}}_001',
          message: error instanceof Error ? error.message : '未知错误',
        },
      },
      { status: 500 }
    );
  }
}
```

### 使用模板

```
用组件模板创建一个 UserCard 组件，展示用户头像和名字
```

Claude Code 会根据模板生成代码，保持风格统一：

```typescript

  className?: string;
  children?: React.ReactNode;
}

/**
 * UserCard 组件
 *
 * @description 展示用户头像和名字

  className = '',
  children,

  return (
    <div className={`flex items-center gap-3 ${className}`}>

};

```

## 📝 方法四：常用 Prompt 存储

### 代码审查 Prompt

**.claude/prompts/review.md**

```markdown
请审查以下代码，从四个维度给出意见：

1. 🐛 正确性：是否有 Bug？边界情况是否处理？
2. 📐 规范性：是否符合项目代码规范？
3. ⚡ 性能：是否有明显性能问题？
4. 🔒 安全性：是否有安全隐患（XSS、注入等）？

输出格式：
| 维度 | 问题 | 建议 | 严重程度 |
|------|------|------|----------|
| 正确性 | xxx | xxx | 🔴高/🟡中/🟢低 |
```

### 测试生成 Prompt

**.claude/prompts/test.md**

```markdown
为以下代码生成完整的测试用例：

要求：
1. 覆盖正常路径（happy path）
2. 覆盖边界情况（空值、极值、特殊字符）
3. 覆盖错误路径（异常、权限不足）
4. 使用 Jest + React Testing Library
5. 每个 describe 块不超过 5 个 it
6. 测试描述用中文

输出要求：
- 先列测试计划（describe + it 清单）
- 确认后再生成完整代码
```

### 文档生成 Prompt

**.claude/prompts/docs.md**

```markdown
为以下代码生成 API 文档：

格式要求：
1. 接口描述（一句话说清楚做什么）
2. 请求方法和路径
3. 请求参数表格（参数名 | 类型 | 必填 | 说明）
4. 响应格式（成功 + 失败）
5. 示例（curl 命令）
6. 注意事项（限流、权限等）
```

### 使用存储的 Prompt

```
用 review prompt 审查 src/utils/format.ts
```

Claude Code 会按照你定义的审查维度和输出格式来执行，不用每次重新描述要求。

## 📝 实战案例：团队共享配置

### 场景

5 人团队，每人都在用 Claude Code，但写出来的代码风格五花八门。怎么统一？

### 方案：配置即代码

```
team-claude-config/
├── README.md                    # 使用说明
├── .claude/
│   ├── instructions.md          # 团队通用规范
│   ├── templates/
│   │   ├── react-component.tsx  # React 组件模板
│   │   ├── api-handler.ts       # API 处理器模板
│   │   ├── hook.ts              # 自定义 Hook 模板
│   │   └── test-file.test.ts    # 测试模板
│   └── prompts/
│       ├── code-review.md       # 代码审查 Prompt
│       ├── generate-docs.md     # 文档生成 Prompt
│       └── refactor.md          # 重构 Prompt
└── scripts/
    └── setup.sh                 # 一键安装到项目
```

### 一键安装脚本

**scripts/setup.sh**

```bash
#!/bin/bash
# 将团队 Claude Code 配置安装到当前项目

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
TARGET_DIR="$(pwd)/.claude"

echo "🚀 安装团队 Claude Code 配置..."

# 备份已有配置
if [ -d "$TARGET_DIR" ]; then
  echo "📦 备份已有配置到 .claude.backup"
  cp -r "$TARGET_DIR" "${TARGET_DIR}.backup"
fi

# 复制团队配置
cp -r "$SCRIPT_DIR/../.claude" "$TARGET_DIR"

# 追加项目特有指令（不覆盖）
if [ -f "${TARGET_DIR}.backup/instructions.md" ]; then
  echo "" >> "$TARGET_DIR/instructions.md"
  echo "# 项目特有配置" >> "$TARGET_DIR/instructions.md"
  cat "${TARGET_DIR}.backup/instructions.md" >> "$TARGET_DIR/instructions.md"
  echo "✅ 已合并项目特有配置"
fi

echo "✅ 安装完成！"
echo "📝 配置文件：$TARGET_DIR/instructions.md"
```

### 使用方式

```bash
# 在项目根目录执行
bash /path/to/team-claude-config/scripts/setup.sh
```

### 团队 instructions.md 示例

```markdown
# 团队编码规范

## 语言
- 代码注释用中文，变量名/函数名用英文
- Git commit message 用 Conventional Commits 格式，描述用中文
  - ✅ `feat: 添加用户登录功能`
  - ❌ `feat: add user login`

## React 组件
- 函数式组件 + Hooks，禁止 class 组件
- Props 必须定义 TypeScript 接口
- 样式用 Tailwind + shadcn/ui，禁止 inline style
- 组件文件结构：imports → types → component → exports

## API 接口
- RESTful 风格，版本号 /api/v1/
- 统一响应格式（见模板）
- 错误码参考 docs/error-codes.md

## 测试
- 核心业务逻辑 100% 覆盖
- 使用 Jest + React Testing Library
- 测试文件与源文件同目录：Component.tsx → Component.test.tsx

## Git
- 分支命名：feature/xxx, fix/xxx, refactor/xxx, chore/xxx
- 提交前必须通过 lint 和测试（husky pre-commit）
- PR 至少 1 人 review 才能合并
```

## 📝 实战案例：CLAUDE.md 项目说明文件

### 什么是 CLAUDE.md

放在项目根目录的 `CLAUDE.md` 文件，是 Claude Code 打开项目时自动加载的上下文。相当于给 AI 助手一份项目"入职手册"。

### CLAUDE.md 示例

```markdown
# 项目：电商平台后台管理系统

## 快速开始
```bash
npm install
cp .env.example .env.local  # 需要配置数据库地址
npm run dev                  # 启动开发服务器 http://localhost:3000
```

## 项目结构
```
src/
├── app/          # Next.js App Router 页面
├── components/   # UI 组件（shadcn/ui 基础上封装）
├── lib/          # 工具函数和配置
├── hooks/        # 自定义 Hooks
├── types/        # TypeScript 类型定义
└── services/     # API 调用层
```

## 重要约定
- 页面组件放在 app/ 下，路由即文件路径
- 业务组件放在 components/ 下，按功能模块分文件夹
- API 调用统一走 services/ 层，组件里不要直接 fetch
- 数据库操作用 Prisma，schema 在 prisma/schema.prisma

## 常用命令
- `npm run dev` — 开发服务器
- `npm run build` — 生产构建
- `npm run test` — 运行测试
- `npm run lint` — ESLint 检查
- `npx prisma studio` — 数据库可视化

## 已知问题
- 首页加载慢（正在优化，见 Issue #89）
- 搜索功能不支持模糊匹配（计划下个迭代）

## 不要做的事
- 不要修改 prisma/schema.prisma 除非明确要求
- 不要安装新的 UI 库，先看 shadcn/ui 有没有
- 不要创建新的环境变量，先用现有的
```

### 效果

Claude Code 打开项目后，自动知道：
- 怎么启动项目
- 代码放在哪里
- 有什么约定
- 什么不该做

你不再需要每次开始对话时说"这是 Next.js 项目，用 Prisma……"，它已经知道了。

## 📝 实战案例：多环境配置管理

### 场景

开发、测试、生产三个环境，配置各不同。让 Claude Code 帮你管理。

### 配置文件体系

```
.env.example          # 模板（提交到 Git）
.env.local            # 本地开发（不提交）
.env.test             # 测试环境（不提交）
.env.production       # 生产环境（不提交，通过 CI 注入）
```

### .env.example 模板

```bash
# 数据库
DATABASE_URL=postgresql://user:pass@localhost:5432/dbname

# 认证
JWT_SECRET=your-secret-key-min-32-chars
JWT_EXPIRES_IN=7d

# 第三方服务
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=noreply@example.com
SMTP_PASS=

# 可选
REDIS_URL=redis://localhost:6379
SENTRY_DSN=
```

### 在 instructions.md 中告诉 Claude Code

```markdown
## 环境变量管理规则

1. 创建新功能需要新环境变量时：
   - 先添加到 `.env.example`（带默认值和注释）
   - 代码中用 `process.env.XXX` 读取
   - 提醒我更新本地 `.env.local` 文件

2. 环境变量读取方式：
   ```typescript
   // ✅ 正确：带默认值
   const dbUrl = process.env.DATABASE_URL || 'postgresql://localhost:5432/dev';

   // ❌ 错误：无默认值，可能 undefined
   const dbUrl = process.env.DATABASE_URL;
   ```

3. 敏感信息（密钥、密码）永远不写进代码或配置文件
```

## ⚡ 配置层级速查

| 层级 | 文件位置 | 作用范围 | 优先级 |
|------|---------|---------|--------|
| 全局指令 | `~/.claude/instructions.md` | 所有项目 | 最低 |
| 项目指令 | `.claude/instructions.md` | 当前项目 | 中 |
| 项目说明 | `CLAUDE.md` | 当前项目 | 中 |
| 对话指令 | 直接在对话中说 | 当前对话 | 最高 |

**优先级规则：对话指令 > 项目配置 > 全局配置**

## 🎓 学到了什么

1. **全局指令管偏好，项目指令管规范**——不冲突，各有分工
2. **模板让代码风格统一**——团队协作的基石
3. **Prompt 存储省脑力**——审查、测试、文档，一次定义反复使用
4. **CLAUDE.md 是项目入职手册**——AI 也需要 onboarding
5. **配置即代码**——团队配置进 Git，新人 clone 即用

## ⚠️ 注意

- **敏感信息不进配置**：密钥、密码、Token 永远不放 instructions.md
- **指令要精不要多**：10 条核心规则 > 50 条啰嗦要求
- **团队配置进版本控制**：`.claude/` 目录应加入 Git
- **个人偏好放全局**：不要把个人习惯写进团队配置
- **定期清理过时指令**：技术栈升级了，配置也要跟着更新
