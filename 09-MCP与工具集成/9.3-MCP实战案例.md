```bash

## 案例二：线上故障排查全链路

**背景**：凌晨 3 点收到告警，API 接口 502 错误率飙升。需要在最短时间内定位问题。

### 前置配置

```json
{
  "mcpServers": {
    "postgres": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-postgres"],
      "env": {
        "DATABASE_URL": "postgresql://user:pass@localhost:5432/myapp"
      }
    },
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "/var/log/myapp"]
    },
    "brave-search": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-brave-search"],
      "env": {
        "BRAVE_API_KEY": "你的key"
      }
    }
  }
}
```

### 排查过程

```bash
# 第一步：看日志
你：读取 /var/log/myapp/error.log 最后 100 行，找出高频错误
Claude：[读取日志]
高频错误：
  1. "Connection pool exhausted" - 出现 847 次
  2. "Timeout after 30000ms" - 出现 203 次
  3. "ECONNREFUSED 127.0.0.1:5432" - 出现 156 次

# 第二步：查数据库连接
你：查看当前数据库连接数，以及 max_connections 配置
Claude：[查询数据库]
当前连接数：198 / 200 (max_connections)
⚠️ 连接池已满！

# 第三步：找连接泄漏
你：查询 pg_stat_activity 中状态为 'idle' 超过 10 分钟的连接
Claude：[查询]
发现 67 个空闲连接超过 10 分钟，最早的一个已空闲 3 小时。
大多数来自 'order-service' 的查询。

# 第四步：确认根因
你：搜索 PostgreSQL "idle connections not released" connection pool 最佳实践
Claude：[搜索]
根据 PostgreSQL 官方文档和社区经验，问题通常是：
1. 应用未正确释放连接（最可能）
2. 连接池配置过小
3. 慢查询导致连接被占用

# 第五步：生成修复方案
你：根据以上分析，生成一份故障报告和修复建议，保存到 ~/incident-reports/2025-05-17-502.md
Claude：[生成报告] ✓
```

### 生成的故障报告

```markdown
# 故障报告：API 502 错误

**时间**：2025-05-17 02:47 - 03:23
**影响**：约 36 分钟，影响约 12,000 次请求

## 根因

PostgreSQL 连接池耗尽（198/200），导致新请求无法获取数据库连接。

连接泄漏来源：order-service 服务未在异常分支释放数据库连接。

## 修复措施

### 紧急处理（已执行）
- 手动清理 67 个空闲连接
- 重启 order-service 服务

### 长期修复
1. 添加连接超时自动回收（idle_timeout = 300s）
2. order-service 使用连接池代理（PgBouncer）
3. 添加连接池使用率告警（>80% 时触发）
4. 代码 review 确保所有数据库操作使用 try-finally 释放连接
```

### 关键价值

半夜排查故障，**不需要在 5 个工具之间来回切换**。一个对话窗口完成日志分析、数据库查询、知识搜索、报告生成。

## 案例四：代码审计 + 安全扫描

**背景**：接手一个遗留项目，需要快速了解代码质量和安全风险。

### 操作指令

```bash

1. 用 Git MCP 查看最近 3 个月的提交者统计，找出核心开发者

3. 找出所有 TODO、FIXME、HACK 注释
4. 找出超过 200 行的文件，标记可能的"上帝类"
5. 搜索是否使用了已废弃的 npm 包（检查 package.json）
6. 生成审计报告保存到 ~/audit-report.md

Claude：[Git] 分析提交者...
[文件系统] 扫描敏感信息...
[文件系统] 搜索技术债务标记...
[搜索] 查询废弃包列表...
[文件系统] 生成报告...

✅ 审计报告已生成
```

### 报告亮点

```markdown

## 📝 MCP 使用心法

### 选择 MCP 的原则

| 原则 | 说明 |
|------|------|
| **按需加载** | 不用的 MCP 不要配，影响启动速度 |
| **权限最小化** | filesystem 只授权需要的目录 |
| **敏感信息隔离** | API Key 用环境变量，不要硬编码 |
| **先手动验证** | 新 MCP 先手动测试再配到 Claude Code |

### 常见坑

**坑1：MCP 服务器启动失败**

```bash
# 症状：Claude Code 说 MCP 不可用
# 排查：
npx -y @modelcontextprotocol/server-filesystem /tmp  # 手动测试
# 如果报错，通常是 Node.js 版本问题
node -v  # 需要 >= 18
```

**坑2：连接超时**

```bash
# 症状：MCP 操作经常超时
# 原因：数据库在远程服务器，网络延迟
# 解决：在 MCP 配置中增加超时设置
```

**坑3：权限问题**

```bash
# 症状：filesystem MCP 无法写入文件
# 解决：检查目录权限
chmod 755 /path/to/your/project
```

### 进阶技巧

**1. 多项目共享 MCP 配置**

```bash
# 全局配置（所有项目可用）
~/.config/claude/mcp.json

# 项目级配置（仅当前项目）
~/my-project/.claude/mcp.json

# 两份配置会合并，项目级覆盖同名配置
```

**2. MCP 性能监控**

```bash
# 关注 MCP 响应时间，如果某个 MCP 经常超时，考虑：
# 1. 换更快的网络
# 2. 减少查询数据量
# 3. 本地缓存结果
```

**3. 自定义 MCP 服务器**

当现有 MCP 不满足需求时，可以自己写一个：

```typescript
// my-mcp-server.ts
import { Server } from '@modelcontextprotocol/sdk/server/index.js';

const server = new Server(
  { name: 'my-tools', version: '1.0.0' },
  { capabilities: { tools: {} } }
);

server.setRequestHandler('tools/list', async () => ({
  tools: [{
    name: 'get_system_info',
    description: '获取系统信息',
    inputSchema: { type: 'object', properties: {} }
  }]
}));
```

## 小结

MCP 的真正威力不在于单个工具，而在于**组合使用**。当你把数据库、文件系统、搜索引擎、Git、通知系统连在一起，Claude Code 就从一个"会写代码的助手"变成了一个"能完成整个工作流的搭档"。

**记住**：
- 配置 MCP 要精不贪多
- 安全第一，权限最小化
- 先手动验证，再交给 AI
- 组合使用才是王道
